Key points

  • One chat app uses everything from Season 6: WebSocket for chat, SSE for notifications, WebRTC for calls (with the socket for signaling), polling for the admin dashboard.
  • Sending: client UUID + outbox → optimistic bubble → server sequence number + ack → tick. Retries are deduplicated.
  • Surviving and scaling: heartbeats, backoff with jitter, resync since the last sequence, pub/sub, TTL presence, throttled typing, CRDTs for shared notes.

Interview answer

For a chat app I'd use WebSockets for messaging, SSE for one-way notifications, WebRTC for voice and video with the socket as the signaling channel, and simple polling where updates are rare. Messages get client-generated IDs, sit in an outbox until acknowledged, appear optimistically, and are ordered by server sequence numbers with deduplication. Connections use 25-second heartbeats, reconnect with exponential backoff and jitter, and resync from the last sequence before flushing the outbox. Socket servers stay stateless behind pub/sub, presence uses TTL keys sent only to viewers, typing is throttled, and shared notes use a CRDT library.

The analogy

A well-run railway network: different trains for different journeys (transports), numbered tickets so nothing is lost or counted twice (ids, acks, sequence), signals that detect broken tracks (heartbeats), and a central control room connecting every station (pub/sub).

How it works

Common traps

  • One transport for everything adds needless complexity or waste.
  • Server-generated message ids make retries impossible to dedupe.
  • No resync after reconnect loses messages sent while offline.

See it yourself

Use WhatsApp Web with DevTools open: the WS connection for chat, small periodic heartbeat frames, ticks updating as acks arrive, and recovery after toggling Wi-Fi.

Quick quiz

Why use SSE for notifications if chat already uses WebSockets?

Notifications are one-way and can come from other services; SSE is simple, reconnects automatically and works over plain HTTP. (Using the existing socket is also valid; it's a design trade-off.)

What happens to messages typed while offline?

They wait in the outbox with client IDs, shown as pending, and are sent after reconnect and resync; the server dedupes any repeats.

How do messages reach users connected to different servers?

Through a pub/sub layer that all socket servers publish to and subscribe from.

  • Transports: WebSocket for chat, SSE for notifications, WebRTC for calls (socket = signaling), polling for the admin dashboard.
  • Send: client UUID + outbox → optimistic bubble → server seq + ack → tick; retries deduped.
  • Survive: heartbeats 25 s → backoff + jitter → resync since last seq → flush outbox.
  • Scale: dumb socket servers + pub/sub; presence with TTL to viewers only; typing throttled. Shared notes: CRDT library.
