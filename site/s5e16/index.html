429 Too Many Requests

Key points

  • Servers limit how many requests you can make: N per user, IP or API key per time window. Exceed it and you get 429 Too Many Requests.
  • A common algorithm is the token bucket: each request spends a token; tokens refill at a steady rate.
  • On 429, read Retry-After and wait. Avoid hitting limits by debouncing, deduping and caching.

Interview answer

Rate limiting protects APIs from abuse and overload by capping requests per client in a time window, often using a token bucket that refills at a fixed rate and allows short bursts. When a client exceeds it, the server responds with 429 and usually a Retry-After header, plus headers showing the limit and remaining quota. A good client waits as instructed with backoff, and reduces request volume through debouncing, deduplication and caching. Limits per IP are risky because many users behind one office or mobile carrier NAT share an IP, so per-user or per-key limits are fairer.

The analogy

A metro token machine at the gate: you need a token to enter, and the machine refills a few tokens every minute. A rush of people empties it, and the rest must wait for refills.

How it works

HTTP/1.1 429 Too Many Requests
Retry-After: 30
x-ratelimit-limit: 60
x-ratelimit-remaining: 0
x-ratelimit-reset: 1763640000

Common traps

  • Retrying immediately on 429 makes it worse. Respect Retry-After.
  • Per-IP limits block entire offices or colleges behind one public IP. Prefer per-user or per-key limits.
  • Search-as-you-type without debounce can burn through a limit quickly.

See it yourself

Open https://api.github.com/users/torvalds and check the response headers: x-ratelimit-limit: 60 and x-ratelimit-remaining drop with each unauthenticated request.

Quick quiz

What does a 429 response mean?

Too Many Requests: you've exceeded the rate limit and should wait before retrying.

How does a token bucket allow bursts?

A full bucket can spend several tokens quickly; after that, requests are limited to the refill rate.

Three ways a client can avoid hitting rate limits?

Debounce input-driven requests, deduplicate concurrent requests, and cache responses.

  • Rate limits: N requests per user / IP / key per window. Token bucket: each request spends a token; tokens refill steadily.
  • See it: api.github.com headers x-ratelimit-limit: 60, x-ratelimit-remaining, x-ratelimit-reset (unauthenticated).
  • On 429: read Retry-After and wait. Be a good client: debounce, dedupe, cache.
  • Trap: per-IP limits block whole offices behind one NAT → limit per user / API key.
