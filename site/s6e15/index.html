IQ: staying alive

1 min read
On this page

  • Interview answer
  • Quick quiz

Key points

  • Revision episode: interview questions on keeping real-time apps alive.
  • Know why a sleeping laptop shows "online" for hours, what causes a crash loop after a restart, why users see their own message twice, and how a message reaches a user on another server.

Interview answer

Real-time systems need heartbeats with TTL-based presence to detect dead connections, reconnects with exponential backoff and jitter plus gradual draining to avoid reconnect storms, client-generated message IDs with deduplication so retries are safe, and a pub/sub layer so messages reach users connected to other servers.

Quick quiz

A user's laptop sleeps, but they show "online" for hours. Why, and the fix?

The connection is half-open, so no close event was delivered. Use app-level heartbeats that time out dead connections, and presence keys with a TTL renewed by each heartbeat.

After a server restart, the new servers crash under load. Why?

Every client reconnects instantly at the same moment (thundering herd). Use exponential backoff with jitter and drain servers gradually during deploys.

Users sometimes see their own message twice. Why?

An ack was lost, the client retried, and the server stored it again. Give each message a client-generated UUID, dedupe on the server, and merge the client's own echo by id.

Alice is on server A, Bob on server B. How does Alice's message reach Bob?

Through pub/sub (Redis, Kafka, NATS): A publishes to Bob's channel, B is subscribed and pushes it down Bob's socket. Sticky sessions don't solve this.

  • Laptop sleeps, "online" for hours (half-open → heartbeats + TTL) · restart crash loop (herd → backoff + jitter, drain) · own message twice (lost ack → client UUID, dedup) · cross-server delivery (pub/sub, not sticky sessions).
