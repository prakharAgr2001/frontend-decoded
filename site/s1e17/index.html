16 ms frame budget

TL;DR

  • On a 60 Hz screen the browser draws a frame every ~16.7 ms. On 120 Hz screens it's ~8.3 ms.
  • Your JS + style + layout + paint must fit inside that budget, or frames get dropped (jank). Aim for about 10 ms of your own work.
  • Use requestAnimationFrame for visual updates: it runs once per frame, right before paint, and pauses in background tabs.

Say it in the interview

At 60 Hz each frame has about 16.7 ms, and the browser needs part of that for style, layout, paint and compositing, so my JavaScript should take roughly 10 ms or less per frame. For visual updates I use requestAnimationFrame, which runs right before the next paint and syncs with the display's refresh rate, and I compute motion from the timestamp it provides rather than assuming a fixed frame rate. setInterval isn't synced to frames, so it can drift and update twice or not at all in a frame.

The analogy

A train that leaves the platform every 16.7 ms, whether you're on it or not. If your work isn't done when it leaves, your update waits for the next train, and the user sees a stutter.

How it works

// ✅ Smooth, time-based movement: same speed on 60 Hz and 120 Hz screens
let start;
function step(now) {
  start ??= now;
  const x = Math.min((now - start) * 0.2, 300);   // 0.2 px per ms
  box.style.transform = `translateX(${x}px)`;
  if (x < 300) requestAnimationFrame(step);
}
requestAnimationFrame(step);

Traps interviewers love

  • ⚠️ Frame-count based motion. x += 2 per frame moves twice as fast on a 120 Hz phone. Use the timestamp.
  • ⚠️ setInterval(fn, 16) for animation. Not aligned with paint: some frames get two updates, some get none.
  • ⚠️ Heavy work inside rAF. rAF doesn't make slow code fast; it only schedules it at the right moment.

See it yourself

DevTools → Performance → record while scrolling or animating. The Frames row shows each frame; long red bars are dropped frames.

Quick quiz

What's the frame budget at 60 fps and 120 fps?

About 16.7 ms and 8.3 ms.

When does a requestAnimationFrame callback run?

Once per frame, just before the browser does style, layout and paint for that frame. It's paused in hidden tabs.

Why use the rAF timestamp instead of counting frames?

Refresh rates differ and frames can be dropped, so movement based on elapsed time stays the same speed on every device.

  • 60 Hz ≈ 16.7 ms per frame (120 Hz ≈ 8.3 ms). Keep your JS ≲ 10 ms.
  • requestAnimationFrame runs right before paint, once per frame, pauses in background tabs. Use its timestamp (time-based motion).
  • setInterval drifts against frames.
