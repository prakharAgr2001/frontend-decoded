Key points

  • Revision episode: interview questions on async edge cases.
  • Know Promise.all vs allSettled, fixing a search race, handling a POST that times out, and replacing one big spinner.

Interview answer

I treat every async flow as unreliable: run independent requests in parallel and choose all or allSettled based on whether partial data is useful, cancel or ignore stale requests, retry only safe operations with backoff and idempotency keys, and design loading and error states per section rather than for the whole page.

Quick quiz

Promise.all vs Promise.allSettled?

all rejects as soon as one promise fails (use when every result is required). allSettled waits for all and reports each outcome (use when partial results are useful).

Search results sometimes show an older query. How do you fix it?

Abort the previous request with AbortController or ignore stale responses with a cleanup flag; debounce to reduce requests; or key results by query (React Query).

A "Place order" POST times out. Do you retry?

Only safely: send an Idempotency-Key so the server can detect duplicates, check the order status before retrying, and use exponential backoff with jitter.

The whole page shows one spinner until everything loads. How do you improve it?

Split into grouped Suspense boundaries with matching skeletons, show critical content first, stream with SSR, and isolate failures with error boundaries.

  • all vs allSettled · search race (abort / ignore stale, debounce, key by query) · POST timeout (idempotency key, status check, backoff + jitter) · one big spinner (split Suspense boundaries, skeletons, streaming).
