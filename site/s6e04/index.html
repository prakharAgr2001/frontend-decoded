Key points

  • Server-Sent Events (SSE) = one HTTP response that never ends, with Content-Type: text/event-stream. The server writes events into it whenever it wants.
  • In the browser: new EventSource('/stream'). It reconnects automatically and sends Last-Event-ID so the server can resume.
  • Limits: one-way (server → client; send with a normal POST) and text only.

Interview answer

SSE keeps a single HTTP response open and streams text events in a simple format with id, event and data fields. The EventSource API handles parsing and automatic reconnection, and on reconnect it sends the Last-Event-ID header so the server can replay missed events. It's ideal when the server pushes and the client mostly listens, like notifications, live scores or streaming AI responses, and it stays plain HTTP, so it works with existing auth, proxies and load balancers. Under HTTP/1.1 each stream holds one of the roughly six connections per origin, which HTTP/2 multiplexing avoids.

The analogy

A radio station. You tune in once and keep listening; the station broadcasts whenever there's news. If you lose signal, your radio retunes automatically. But you can't talk back through the radio.

How it works

HTTP/1.1 200 OK
Content-Type: text/event-stream

id: 41
event: score
data: {"match":"IND-AUS","runs":187}

id: 42
event: score
data: {"match":"IND-AUS","runs":191}

const source = new EventSource('/api/live-score');
source.addEventListener('score', e => updateScore(JSON.parse(e.data)));
source.onerror = () => showReconnecting();          // EventSource retries by itself

// Sending goes over normal HTTP
fetch('/api/predictions', { method: 'POST', body: JSON.stringify({ pick: 'IND' }) });

Common traps

  • The 7th tab hangs on HTTP/1.1: browsers allow about 6 connections per origin, and each open stream holds one. Use HTTP/2, or share one stream across tabs.
  • Buffering proxies or compression can hold events back. Disable buffering for the stream.
  • Binary data isn't supported; use WebSockets or base64.

See it yourself

On ChatGPT or Claude's web app, DevTools → Network → the response to a sent message is often an event stream: its EventStream tab shows events arriving one by one.

Quick quiz

How does SSE resume after a disconnect?

EventSource reconnects automatically and sends the Last-Event-ID header; the server replays events after it.

How does a client send data when using SSE?

With ordinary HTTP requests (fetch POST); SSE itself is one-way.

Why might a 7th SSE tab not connect?

HTTP/1.1's ~6 connections per origin limit; each stream holds one. HTTP/2 multiplexes them on one connection.

  • One HTTP response that never ends: Content-Type: text/event-stream. Format: id:, event:, data: lines, blank line ends an event.
  • new EventSource('/stream') → onmessage. Auto-reconnects and sends Last-Event-ID so the server can resume.
  • Limits: one-way (send with normal fetch POST), text only.
  • Trap: HTTP/1.1 ≈ 6 connections per origin; each open stream holds one → 7th tab hangs. HTTP/2 multiplexes streams on one connection.
