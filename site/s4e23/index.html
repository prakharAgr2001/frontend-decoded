Key points

  • One food-delivery app uses every kind of state, each in the right home.
  • URL for search and filters, local state for dropdowns, a server cache for the menu, a store with selectors for the cart, context for theme and user, a form library for the address, a state machine for payment.
  • Plus normalized orders, optimistic likes with rollback, and Immer for updates.

Interview answer

In a food-ordering app I'd keep search and filters in the URL so results are shareable, small UI toggles in local state, the menu and restaurant data in a server-state cache, the cart in a lightweight store with selectors for the badge and derived totals, and app-wide values like theme and user in context. The address form uses a form library with schema validation and invalidates the address query on save. Payment is a state machine so double submits are impossible, orders are normalized by ID, favourites use optimistic updates with rollback, and nested updates use Immer.

The analogy

A restaurant kitchen where every ingredient has its place: spices by the stove, vegetables in the fridge, today's specials on the board at the door. Things go wrong when everything is dumped in one cupboard.

How it works

Common traps

  • Putting the menu in the cart store. Server data in a client store goes stale.
  • Booleans for payment (isPaying, isPaid, hasError): use a machine.
  • Cart total in state instead of derived with a selector.

See it yourself

Open Swiggy or Zomato on the web: change filters and watch the URL, add to cart and refresh, and notice which data survives where.

Quick quiz

Where does the restaurant menu live, and why?

In a server-state cache: it's owned by the server, can change, and should be cached and refetched when stale.

How should the cart badge get its count?

Through a selector on the cart store, so it re-renders only when the count changes and the count is derived, not stored.

Why model payment as a state machine?

To make impossible states unrepresentable and ignore repeated "Pay" events during processing, preventing double charges (along with an idempotency key on the server).

  • URL (search + filters) · local (dropdown) · server cache (menu) · store + selectors (cart, badge, derived total) · context (theme, user) · form library (address) + invalidation · state machine (payment) · normalized orders · optimistic like + rollback · Immer updates.
