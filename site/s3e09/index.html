Critical rendering path

Key points

  • The critical rendering path is everything the browser needs before the first pixels: HTML → DOM, CSS → CSSOM → render tree → paint.
  • CSS is render-blocking (no paint until it's loaded). A plain <script> is parser-blocking (HTML parsing stops until it runs).
  • Shrink the path: inline critical CSS, load the rest without blocking, and defer scripts.

Interview answer

The critical rendering path is the sequence from receiving HTML to the first paint: building the DOM, building the CSSOM, combining them into the render tree, then layout and paint. Stylesheets block rendering and synchronous scripts block parsing, and a script also waits for any stylesheet before it. To speed up first paint I inline the small amount of CSS needed above the fold, load the remaining CSS asynchronously or with media queries, and defer scripts so they don't block parsing.

The analogy

Opening a shop in the morning. You can't open the shutters until the essentials are on the shelves (critical CSS). The stockroom can be organised after customers walk in.

How it works

<head>
  <style>/* critical above-the-fold CSS, inlined */</style>
  <link rel="stylesheet" href="/print.css" media="print">         <!-- doesn't block screen rendering -->
  <link rel="preload" href="/rest.css" as="style" onload="this.rel='stylesheet'">
  <script src="/app.js" defer></script>
</head>

Common traps

  • A script after a stylesheet waits for that CSS, because scripts may read styles. So CSS can indirectly block parsing too.
  • Huge inlined CSS makes the HTML heavier and isn't cached. Inline only what's needed above the fold.
  • @import inside CSS creates a chain: one file must download before the next is discovered.

See it yourself

Lighthouse → "Eliminate render-blocking resources" lists the CSS/JS delaying first paint. In the Performance panel, request details show Render blocking: Blocking.

Quick quiz

Why is CSS render-blocking but not parser-blocking?

The browser can keep building the DOM, but it won't paint without styles to avoid a flash of unstyled content.

How can CSS end up blocking parsing?

A synchronous script that follows a stylesheet waits for that stylesheet to load, and the parser waits for the script.

Name two ways to load non-critical CSS without blocking render.

Use a media attribute that doesn't match (e.g. media="print", then switch), or preload it and swap rel to stylesheet on load.

  • HTML → DOM, CSS → CSSOM → render tree → first pixels. CSS is render-blocking; plain <script> is parser-blocking.
  • Shrink it: inline critical CSS, load the rest non-blocking, media="print" for non-critical sheets, defer scripts.
  • See it: Lighthouse "Render blocking requests"; Performance panel request details "Render blocking". Trap: a script after a stylesheet waits for that CSS → CSS can block parsing too.
