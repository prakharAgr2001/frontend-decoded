Heartbeats

Key points

  • A dead connection doesn't announce itself. If a laptop sleeps or Wi-Fi drops, the socket can stay "open" on both sides (a half-open connection), and the app shows "online" forever.
  • Proxies and load balancers also kill connections that stay idle too long.
  • Fix: an app-level ping/pong heartbeat. If nothing arrives within the interval plus a margin, close the socket and reconnect.

Interview answer

TCP connections can silently die: when a device sleeps or the network changes, neither side necessarily gets a close event, leaving a half-open connection. Intermediaries also drop idle connections after their timeout. So I add an application-level heartbeat: the server sends a ping every 25 to 30 seconds, any incoming message resets a timer on the client, and if the timer exceeds the interval plus a margin the client closes and reconnects. Browsers answer protocol-level ping frames automatically but don't expose them to JavaScript, so apps send their own ping messages. The interval must be shorter than the smallest idle timeout on the path but not so frequent that it drains mobile batteries.

The analogy

On a phone call where the other side has gone quiet, you say "hello? are you there?" every half minute. If nobody answers, you hang up and call back instead of holding a dead line forever.

How it works

let deadTimer;
function resetHeartbeat(ws) {
  clearTimeout(deadTimer);
  deadTimer = setTimeout(() => ws.close(), 35_000);    // 30 s ping + 5 s margin
}
ws.onopen = () => resetHeartbeat(ws);
ws.onmessage = e => {
  resetHeartbeat(ws);
  const msg = JSON.parse(e.data);
  if (msg.type === 'ping') return ws.send(JSON.stringify({ type: 'pong' }));
  handle(msg);
};

Common traps

  • Interval longer than a proxy's idle timeout (often 20–30 s or more): the proxy cuts the connection before your ping.
  • Too frequent pings drain phone batteries and data.
  • Trusting navigator.onLine: it only knows if there's a network interface, not if your server is reachable.

See it yourself

WhatsApp Web → DevTools → Network → WS → Messages: you'll see small periodic frames even when nobody is chatting.

Quick quiz

What is a half-open connection?

One side thinks the connection is open while the other side (or the network path) is gone, with no close event delivered.

Why can't browser JS rely on protocol-level ping frames?

Browsers answer them automatically but don't expose them, and JS can't send them, so apps implement their own ping messages.

How do you choose the heartbeat interval?

Shorter than the smallest idle timeout along the path (proxies, load balancers), but long enough not to waste battery and data.

  • A dead TCP connection doesn't announce itself (sleep, Wi-Fi drop) → half-open connection; app shows "online" forever. Proxies also kill idle connections.
  • App-level ping/pong: every message resets a timer; silence > interval + margin (e.g. 35 s for 30 s pings) → ws.close() → reconnect.
  • Browsers answer protocol ping frames silently, and JS can't send them → apps send their own {type:'ping'}.
  • Trap: interval must be under the shortest idle timeout on the path (often 20–30 s), but not so fast it drains batteries.
