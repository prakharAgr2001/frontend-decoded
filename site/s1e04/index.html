HTTPS & the padlock

TL;DR

  • HTTPS = HTTP inside TLS. TLS gives three promises: encryption (nobody can read it), integrity (nobody can change it), authentication (you're talking to the real site).
  • The site proves who it is with a certificate signed by a Certificate Authority your browser already trusts.
  • The padlock means the connection is private. It does not mean the site is safe or honest.

Say it in the interview

HTTPS is HTTP over TLS. During the TLS handshake the client and server agree on encryption keys using key exchange, and the server presents a certificate chain that the browser verifies up to a trusted root CA. After that, all traffic is encrypted and tamper-proof. TLS 1.3 needs one round trip for the handshake. The padlock only guarantees a secure connection to that domain, not that the domain is trustworthy.

The analogy

Sending a letter in a locked box. Encryption: only the receiver has the key. Integrity: a broken seal shows tampering. Authentication: the box comes with an ID card stamped by a government office (the CA) you trust. The ID proves who they are, not that they're a nice person.

How it works

The certificate chain:

  • If any link fails (expired, wrong domain, untrusted issuer), the browser shows the full-page warning.
  • Free certificates (Let's Encrypt) made HTTPS the default; most browsers now flag plain HTTP as "Not secure".

Traps interviewers love

  • ⚠️ "Padlock = safe site." Phishing sites get valid certificates too. The padlock only proves the connection is encrypted to that domain.
  • ⚠️ Mixed content. An HTTPS page loading a script over http:// gets it blocked (scripts) or flagged (images).
  • ⚠️ "HTTPS is slow." With TLS 1.3, session resumption and HTTP/2 (which needs HTTPS in browsers), it's usually faster than plain HTTP.

See it yourself

Click the padlock / site-info icon → Connection is secure → Certificate is valid to see the chain. DevTools → Security tab shows the TLS version and cipher.

Quick quiz

What three things does TLS guarantee?

Confidentiality (encryption), integrity (tampering is detected), and authentication (the server proves its identity with a certificate).

How does the browser know a certificate is real?

It follows the chain of signatures from the site's certificate to an intermediate CA to a root CA that's in the browser/OS trust store, and checks the domain name and expiry.

Why is HTTP/2 usually only available over HTTPS?

Browsers only implement HTTP/2 over TLS (protocol negotiated during the TLS handshake via ALPN), so in practice HTTPS is required.

  • HTTPS = HTTP over TLS. 3 promises: encryption, integrity, authentication.
  • Certificate chain: root CA (trusted by browser) → intermediate → site. TLS 1.3 handshake = 1 round trip (TLS 1.2 = 2).
  • Trap: padlock = private connection, not a safe site. Phishing sites have valid certs.
