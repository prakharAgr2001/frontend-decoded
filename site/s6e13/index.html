Scaling WebSockets

Key points

  • Sockets are stateful: Alice is connected to server A, Bob to server B. Server A can't write to Bob's socket.
  • Fix: pub/sub (Redis, Kafka, NATS). Server A publishes to user:bob; server B is subscribed and pushes it down Bob's socket.
  • Keep socket servers simple, scale them out, and on deploys drain gradually so clients reconnect with jitter.

Interview answer

With multiple WebSocket servers, each user's connection lives on one specific server, so a message for a user connected elsewhere must be routed. I use a pub/sub layer like Redis, Kafka or NATS: each socket server subscribes to channels for its connected users or rooms, and any server publishes events to those channels. Socket servers stay stateless apart from connections and scale horizontally behind a load balancer that supports upgrades and long idle timeouts. Deploys close every socket on a server, so I drain servers gradually and rely on client backoff with jitter. Sticky sessions only help a reconnect land on the same server; they don't solve cross-server delivery.

The analogy

Two call centres in different cities. A customer on a call in Pune needs a message passed to one on a call in Delhi. The Pune agent posts it on a shared internal board, and the Delhi agent watching that board reads it out to their caller.

How it works

// Socket server (Node + ws + Redis)
wss.on('connection', (ws, req) => {
  const userId = authenticate(req);
  subscriber.subscribe(`user:${userId}`, msg => ws.send(msg));
  ws.on('message', raw => {
    const { to, text } = JSON.parse(raw);
    publisher.publish(`user:${to}`, JSON.stringify({ from: userId, text }));
  });
});

Common traps

  • Sticky sessions as the fix. They don't deliver messages between servers.
  • Deploying all servers at once drops every connection simultaneously → reconnect storm.
  • Load balancer idle timeouts shorter than your heartbeat interval.

See it yourself

Run two instances of a small WebSocket server on different ports with a shared Redis, connect one client to each, and send messages between them through pub/sub.

Quick quiz

Why can't server A send directly to Bob?

Bob's socket lives on server B; A has no connection to him.

Do sticky sessions solve cross-server messaging?

No. They only route a client back to the same server; messages still need pub/sub to reach users on other servers.

How do you deploy socket servers without a reconnect storm?

Drain servers gradually (stop new connections, close existing ones over time) and rely on clients reconnecting with backoff and jitter.
