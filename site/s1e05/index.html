HTTP/1.1 vs 2 vs 3

TL;DR

  • HTTP/1.1: one request at a time per connection, so browsers open about 6 connections per site.
  • HTTP/2: many requests at once on one connection (multiplexing) + compressed headers. But it still runs on TCP, so one lost packet stalls every stream.
  • HTTP/3: runs on QUIC over UDP. Streams are independent, handshakes are faster, and connections survive switching from Wi-Fi to mobile data.

Say it in the interview

HTTP/1.1 handles one request at a time per connection, so browsers open around six parallel connections and requests queue behind each other. HTTP/2 multiplexes many streams over a single TCP connection and compresses headers, but a lost TCP packet blocks all streams. HTTP/3 replaces TCP with QUIC on UDP, so each stream recovers loss independently, the handshake is combined with TLS, and connections can migrate between networks.

The analogy

A toll plaza. HTTP/1.1 = 6 booths, each car pays fully before the next moves. HTTP/2 = one huge booth processing many cars at once, but if one car breaks down, the whole lane stops. HTTP/3 = many independent lanes; a breakdown only blocks its own lane.

How it works

  • HTTP/1.1 tricks like domain sharding, sprites and bundling everything existed to work around the 6-connection limit. With HTTP/2 they're mostly unnecessary, sometimes harmful.
  • HTTP/2 server push was removed from Chrome; preload and 103 Early Hints replaced it.

Traps interviewers love

  • ⚠️ "HTTP/2 is always faster." On lossy mobile networks, one connection with TCP head-of-line blocking can lose to several HTTP/1.1 connections.
  • ⚠️ Confusing the two kinds of head-of-line blocking. HTTP/2 fixed it at the HTTP level (requests no longer queue). HTTP/3 fixed it at the transport level (packet loss).
  • ⚠️ "UDP means unreliable." QUIC adds its own reliability and encryption on top of UDP.

See it yourself

DevTools → Network → right-click the column header → enable Protocol. You'll see http/1.1, h2 and h3 side by side.

Quick quiz

What is multiplexing in HTTP/2?

Sending many requests and responses at the same time over one connection, split into interleaved frames tagged with stream IDs.

Why did HTTP/3 move away from TCP?

TCP's strict in-order delivery means one lost packet blocks all multiplexed streams, and TCP can't be changed easily because it lives in operating systems and middleboxes. QUIC on UDP fixes loss per stream and can evolve in user space.

Is bundling all JS into one big file still a good idea with HTTP/2?

Not necessarily. Many smaller files are cheap with multiplexing and cache better (one change doesn't invalidate everything). Very large numbers of tiny files still have overhead, so moderate code splitting wins.

  • 1.1: one request per connection at a time → ~6 connections per site.
  • 2: multiplexing + header compression on ONE TCP connection — but a lost packet stalls all streams.
  • 3: QUIC over UDP, independent streams, survives Wi-Fi → mobile switches. Trap: HTTP/2 isn't always faster on lossy networks.
