Key points

  • Code splitting breaks one big bundle into smaller chunks that load only when needed, using dynamic import().
  • Split by route, by heavy feature (charts, editors, maps), and by below-the-fold components. Shared libraries go in a vendor chunk.
  • Goal: the first page downloads and runs only its own code.

Interview answer

Code splitting uses dynamic imports so the bundler emits separate chunks that are loaded on demand. I usually split by route first, then lazy-load heavy, rarely used features like rich text editors, charts or maps, and keep shared dependencies in a common chunk so they're cached across routes. The DevTools Coverage tab shows how much downloaded code never runs, which is a good signal for what to split. I avoid splitting too finely, because many tiny chunks create request waterfalls.

The analogy

A travel guidebook split into city booklets. You carry only the city you're visiting today instead of the whole 800-page book.

How it works

// Load the chart library only when the user opens the report
button.addEventListener('click', async () => {
  const { renderChart } = await import('./chart.js');   // separate chunk
  renderChart(data);
});

Common traps

  • Too many tiny chunks → request waterfalls (chunk A loads, then discovers it needs chunk B).
  • Splitting what's always needed just adds a delay.
  • No loading state. Lazy chunks take time; show a fallback.

See it yourself

DevTools → ⋮ → More tools → Coverage → reload. Red bars are code that was downloaded but never executed, your splitting opportunities.

Quick quiz

What creates a split point in modern bundlers?

A dynamic import() expression.

What should you split first?

Routes, then large features used by few users or only after interaction.

What's the risk of over-splitting?

Many small requests and dependency waterfalls that can make loading slower.

  • Dynamic import() → separate chunk loaded on demand. Split by route, heavy feature, below the fold; shared libs in a vendor chunk.
  • See it: DevTools → Coverage (red = downloaded, never ran). Trap: too many tiny chunks → request waterfalls.
