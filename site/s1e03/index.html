TCP handshake

TL;DR

  • Before any data moves, TCP does a three-way handshake: SYN → SYN-ACK → ACK.
  • It costs one full round trip before the first request can even be sent.
  • TCP promises data arrives complete and in order, which is great, until one lost packet holds up everything behind it.

Say it in the interview

TCP is a reliable, ordered connection protocol. To open a connection the client sends SYN, the server replies SYN-ACK, and the client sends ACK, which costs one round trip before any HTTP data. TCP then numbers every packet, retransmits lost ones and delivers them in order. That reliability causes head-of-line blocking, where one lost packet stalls everything behind it, which is a key reason HTTP/3 moved to QUIC over UDP.

The analogy

A phone call. You dial (SYN), they pick up and say "hello?" (SYN-ACK), you say "hi, it's me" (ACK). Only now does the real conversation start. And if a word gets garbled, you ask "sorry, say that again?" before moving on.

How it works

  • Sequence numbers let the receiver put packets back in order and spot gaps.
  • ACKs confirm what arrived. If an ACK doesn't come back, the sender retransmits.
  • Keep-alive reuses an open connection for the next request, so you don't pay the handshake again. In DevTools, reused connections show 0 ms "Initial connection".

Traps interviewers love

  • ⚠️ Head-of-line blocking. TCP must deliver in order, so if packet 3 is lost, packets 4–10 wait in the buffer even though they arrived fine.
  • ⚠️ HTTPS isn't one handshake. It's TCP first, then TLS on top: up to 2 round trips before the request (TLS 1.3 needs one).
  • ⚠️ "TCP is slow, UDP is fast." UDP just skips the guarantees. QUIC (HTTP/3) builds its own reliability on top of UDP without TCP's ordering problem.

See it yourself

DevTools → Network → any request → Timing → Initial connection. Reload: the second time it's usually 0 because the connection was reused.

Quick quiz

How many round trips does a fresh HTTPS connection cost before the first request?

With TLS 1.3: 1 for TCP + 1 for TLS = 2. With TLS 1.2: 1 + 2 = 3. HTTP/3 (QUIC) combines them into 1, or 0 on resumed connections.

Why does keep-alive improve performance?

The connection stays open after a response, so the next request skips the TCP and TLS handshakes entirely.

What is TCP head-of-line blocking?

Because TCP delivers bytes strictly in order, one lost packet blocks delivery of all later packets until it's retransmitted, even if they already arrived.

  • SYN → SYN-ACK → ACK = 1 round trip before any data (e.g. ~200 ms India ↔ US).
  • Keep-alive reuses connections; later requests show 0 ms "Initial connection".
  • Trap: TCP guarantees order, so one lost packet blocks everything behind it (head-of-line blocking) → why HTTP/3 exists.
