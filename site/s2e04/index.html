Server-side rendering (SSR)

Key points

  • In server-side rendering (SSR), the server fetches data and builds the full HTML on every request.
  • The browser paints content immediately; JavaScript then loads and makes the page interactive (hydration).
  • Trade-off: first paint comes sooner, but TTFB (time to first byte) goes up because the server is doing work before responding.

Interview answer

With SSR, each request runs the app on the server: it fetches the data, renders components to HTML and sends a complete page. The user sees content as soon as the HTML arrives, which helps first contentful paint and SEO, and then the client bundle hydrates the page to make it interactive. The cost is higher server load and TTFB, since nothing is sent until rendering finishes, and the page still isn't interactive until hydration completes.

The analogy

A restaurant that cooks your dish fresh when you order. You wait a bit longer before the plate arrives (TTFB), but it arrives ready to eat, unlike the flat-pack kitchen of CSR.

How it works

// Next.js (App Router): this component runs on the server for each request
export const dynamic = 'force-dynamic';
export default async function Product({ params }) {
  const product = await db.product.find(params.id);
  return <h1>{product.title} · ₹{product.price}</h1>;
}

Common traps

  • "SSR is always faster." A slow database or a far-away server makes TTFB huge, and the page can feel slower than CSR.
  • SSR doesn't delete JavaScript. The page still needs the bundle to hydrate before clicks work.
  • Caching matters. Rendering the same page for every visitor is wasted work; cache it or use SSG/ISR where possible.

See it yourself

View Source on an Amazon product page: titles and prices are in the HTML. DevTools → Network → the document request → Timing → "Waiting for server response" roughly equals server render time.

Quick quiz

Which metric gets worse with SSR, and which gets better?

TTFB usually gets worse (the server renders first). First contentful paint usually gets better (HTML arrives with content).

Is an SSR page interactive as soon as it's visible?

No. It becomes interactive only after the JavaScript downloads and hydration attaches event handlers.

When would you choose SSR over SSG?

When the content is personalised or changes per request (user-specific pages, live prices, search results) and must still be visible quickly and crawlable.

  • Every request: server fetches data + builds full HTML → browser paints immediately; JS loads after to make it interactive.
  • TTFB goes up (server is cooking), first paint comes sooner.
  • See it: View Source on Amazon shows titles/prices; Network → document → Timing → "Waiting for server response" ≈ render time.
  • Trap: SSR isn't always faster — slow DB or far server = huge TTFB, and still not interactive until JS. SSR moves work, doesn't delete it.
