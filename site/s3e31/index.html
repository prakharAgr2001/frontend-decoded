Key points

  • A performance budget is an agreed limit your team won't exceed, e.g. JS ≤ 170 KB compressed, LCP ≤ 2.5 s, TBT ≤ 200 ms.
  • Types: quantity (KB, number of requests), timings (LCP, INP), rule-based (Lighthouse score).
  • Enforce it in CI so a pull request that breaks the budget fails, just like a failing test.

Interview answer

A performance budget sets limits on things like bundle size, request counts, or metric timings, so performance doesn't slowly regress. I set initial budgets from current field data, slightly better than today, and tighten them over time. They're enforced automatically in CI with tools like Lighthouse CI assertions or size-limit, so a pull request that exceeds the budget fails and the team has to discuss the trade-off before merging.

The analogy

A monthly spending budget. Without one, small purchases add up and you only notice at the end of the month. A budget makes every new expense a conscious decision.

How it works

// .size-limit.json
[{ "path": "dist/assets/index-*.js", "limit": "170 KB" }]

// lighthouserc.json (assertions)
{ "ci": { "assert": { "assertions": {
  "largest-contentful-paint": ["error", { "maxNumericValue": 2500 }],
  "total-blocking-time": ["error", { "maxNumericValue": 200 }]
} } } }

Common traps

  • Budgets nobody enforces are just wishes. Put them in CI.
  • Unrealistic budgets get ignored. Start from where you are.
  • Testing only on fast machines. Validate on a real mid-range Android phone.

See it yourself

Add size-limit to a project and run it in a GitHub Action: open a PR that adds a big library and watch the check fail.

Quick quiz

What are the three kinds of performance budgets?

Quantity-based (KB, requests), milestone timings (LCP, TBT, INP), and rule-based (Lighthouse scores).

How do you choose initial budget values?

From current measurements, set slightly better than today, then tighten over time.

How do you enforce a budget?

Automated checks in CI (Lighthouse CI, size-limit, bundler limits) that fail the build when exceeded.

  • Agreed limits, e.g. JS ≤ 170 KB compressed, LCP ≤ 2.5 s, TBT ≤ 200 ms. Kinds: quantity, milestone timings, rule-based scores.
  • Enforce in CI: Lighthouse CI assertions, size-limit → fail the PR.
  • IQ: start from current field data, set slightly better, ratchet down, test on a real mid-range phone.
