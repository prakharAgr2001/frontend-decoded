Key points

  • Normalization: store each entity once, keyed by id, and reference it by id everywhere else: users.byId[7], posts.byId[101].author = 7.
  • Wins: one source of truth, updates in one place, O(1) lookups, no deep nested spreads.
  • Tools: RTK createEntityAdapter; Apollo and Relay normalize automatically. React Query caches per query, so you invalidate instead.

Interview answer

Normalizing client state means storing entities in flat lookup tables keyed by ID, with relationships expressed as IDs instead of nested copies. If a user's name changes, I update one record and every post, comment and list that references that ID shows the new name. It also makes lookups constant time and updates simpler. Redux Toolkit's createEntityAdapter provides this shape and helpers, GraphQL clients like Apollo normalize their caches automatically, while query-based caches like React Query keep data per query and rely on invalidation.

The analogy

A school's student register. Each student is written once with a roll number. Class lists, sports teams and the exam seating chart just list roll numbers. When a student changes their surname, you correct one line in the register, not every list.

How it works

import { createEntityAdapter, createSlice } from '@reduxjs/toolkit';
const usersAdapter = createEntityAdapter();
const usersSlice = createSlice({
  name: 'users',
  initialState: usersAdapter.getInitialState(),        // { ids: [], entities: {} }
  reducers: { userUpdated: usersAdapter.updateOne, usersReceived: usersAdapter.setAll },
});

Common traps

  • Copies drifting apart: the same user shows two different names on one screen.
  • Over-normalizing simple data that's only used in one place adds complexity for nothing.
  • Forgetting to denormalize for display: write selectors that join ids back into objects.

See it yourself

Open Redux DevTools on an app using entity adapters: state looks like { ids: [...], entities: { 7: {...} } }.

Quick quiz

What does a normalized state shape look like?

Separate tables per entity type, each with entities keyed by id (and often an ids array for order); relations stored as ids.

Why does normalization prevent inconsistent UI?

Each entity exists once, so every view reading it by id sees the same, latest data.

Does React Query normalize data?

No. It caches per query key; you keep related queries correct through invalidation or setQueryData.

  • Store each entity once, keyed by id; everything else references the id: users.byId[7], posts.byId[101].author = 7.
  • Wins: one source of truth, updates in one place, O(1) lookups, no deep spreads.
  • Tools: RTK createEntityAdapter; Apollo/Relay normalize automatically (__typename + id). React Query caches per query (invalidate instead).
