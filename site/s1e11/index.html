Layout thrashing

Key points

  • Layout thrashing = writing styles and reading layout values back and forth in a loop. Every read forces a fresh layout.
  • 100 items × (write + read) = 100 layouts in one frame instead of 1.
  • Fix: read everything first, then write everything, ideally inside requestAnimationFrame.

Interview answer

The browser normally batches style changes and runs layout once per frame. But if you read a layout property like offsetHeight after writing a style, it has to run layout synchronously to give you a correct value. Doing that write-read pattern in a loop forces layout on every iteration, which is layout thrashing. The fix is to batch all reads first and then all writes, or schedule writes with requestAnimationFrame.

The analogy

Asking a tailor to measure you after every single stitch. "Add a button. How long is the sleeve now? Add another. How long now?" The tailor re-measures the whole shirt every time. Instead: take all measurements first, then do all the stitching.

How it works

// Bad: Thrashing: each read forces layout because the previous write made it dirty
for (const card of cards) {
  card.style.height = card.offsetWidth + 'px';   // read → write → read → write…
}

// Good: Batched: one layout for all reads, then writes are applied together
const widths = cards.map(c => c.offsetWidth);       // all reads
requestAnimationFrame(() => {
  cards.forEach((c, i) => c.style.height = widths[i] + 'px');   // all writes
});

Properties that force layout when read: offsetTop/Left/Width/Height, clientWidth/Height, scrollTop, scrollHeight, getBoundingClientRect(), getComputedStyle() (for layout values).

Common traps

  • "Reading is harmless." Reading is only free if nothing changed since the last layout.
  • Hidden in libraries. jQuery's .height(), measuring scroll position in a scroll handler, or a React effect that measures then sets state can all thrash.
  • Use observers instead of polling. ResizeObserver and IntersectionObserver give you sizes without forcing layout in your own code.

See it yourself

DevTools → Performance → record. Thrashing shows as many tiny purple Layout blocks with a red corner and the warning "Forced reflow is a likely performance bottleneck."

Quick quiz

Why does reading offsetHeight after setting a style cause layout?

The style change made layout invalid. To return an accurate number, the browser must recalculate layout immediately instead of waiting for the next frame.

How do you fix layout thrashing in a loop?

Do all reads first and store them, then do all writes (optionally in requestAnimationFrame), so layout runs once.

Name three properties that force layout when read.

offsetHeight, getBoundingClientRect(), scrollTop (also clientWidth, offsetTop, scrollHeight).

  • Read/write/read/write in a loop → a layout per read. Fix: batch all reads, then all writes; schedule writes in requestAnimationFrame.
  • Shows as "Forced reflow is a likely performance bottleneck" in Performance.
  • Q: layout-forcing reads: offsetHeight/Top, clientWidth, scrollTop, getBoundingClientRect().
