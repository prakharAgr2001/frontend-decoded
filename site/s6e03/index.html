Long polling

Key points

  • In long polling, the server holds the request open until there's news (or a timeout of about 30 s, then an empty response). The client immediately sends the next request.
  • Updates arrive almost instantly, using plain HTTP.
  • Costs: full request and headers per message, and one open request per user. Use a cursor so no messages are lost between polls.

Interview answer

Long polling keeps each request open on the server until new data is available or a timeout expires; the client then immediately reopens it. This gives near real-time delivery over standard HTTP, which works through restrictive proxies and was the classic fallback before WebSockets. It's heavier than a persistent connection because every message needs a new request with full headers. To avoid losing messages that arrive between requests, the client sends the ID of the last message it saw, and the server returns everything after it.

The analogy

Calling a shop and saying "call me back the moment the stock arrives". They keep the line on hold until it does. Once you hang up, you immediately call again to wait for the next delivery.

How it works

async function longPoll(since = 0) {
  while (true) {
    try {
      const res = await fetch(`/api/messages?since=${since}`);     // server holds it open
      const msgs = await res.json();
      msgs.forEach(render);
      if (msgs.length) since = msgs[msgs.length - 1].id;
    } catch {
      await new Promise(r => setTimeout(r, 2000));                 // back off on errors
    }
  }
}

Common traps

  • Messages lost in the gap between one response and the next request. Always send a cursor (since).
  • Proxy and load balancer timeouts shorter than your hold time cut requests early.
  • Server resources: each waiting client holds a request; the server must handle many idle connections efficiently.

See it yourself

DevTools → Network on an app using long polling: requests stay "pending" for a long time, complete, and a new one starts straight away.

Quick quiz

How is long polling different from short polling?

The server holds the request until there's data (or a timeout) instead of answering immediately, so updates arrive almost instantly.

How do you avoid losing messages between long-poll requests?

Send a cursor (last message ID) and have the server return everything after it.

Main cost compared to WebSockets?

A new HTTP request with full headers for every response, plus connection overhead.

  • Server holds the request open until there's news (or ~30 s timeout → empty response), client immediately asks again.
  • Near-instant, plain HTTP. Costs: full request + headers per message, one open request per user.
  • Trap: messages in the gap between polls → send a cursor (?since=<last id>) so the server returns everything after it.
