Key points

  • Zustand: a tiny store with hooks, no Provider needed. Components read slices: useCart(s => s.items.length).
  • Jotai: state as small atoms plus derived atoms. Components re-render only when the atoms they read change.
  • MobX: observable objects you mutate directly; observer components update automatically, like spreadsheet cells.

Interview answer

Zustand is a minimal hook-based store without providers, where components subscribe to slices through selectors. Jotai models state as atoms, composable units with derived atoms, giving fine-grained re-renders. MobX uses observables and automatic dependency tracking, so you mutate state and observer components update. I pick based on team size and style: Zustand for simple shared state, Jotai for many independent pieces, Redux Toolkit for large teams. With server rendering, I never use a module-level store, because it would be shared across requests.

The analogy

Three ways to share notes in an office: Zustand is a shared notice board anyone can read a section of, Jotai is lots of sticky notes where you only watch the ones you care about, MobX is a live spreadsheet where changing one cell updates everything that depends on it.

How it works

// Zustand
import { create } from 'zustand';
const useCart = create(set => ({
  items: [],
  add: item => set(s => ({ items: [...s.items, item] })),
}));
function CartBadge() { return <span>{useCart(s => s.items.length)}</span>; }   // re-renders only when the count changes

// Jotai
import { atom, useAtomValue } from 'jotai';
const itemsAtom = atom([]);
const countAtom = atom(get => get(itemsAtom).length);     // derived atom
function CartBadge() { return <span>{useAtomValue(countAtom)}</span>; }

Common traps

  • SSR with a module-level store: the same store object is shared by all requests on the server, so one user's data can leak to another. Create a store per request and pass it through context.
  • Selecting a new object each time (s => ({ a: s.a, b: s.b })) re-renders every time. Use useShallow or separate selectors.
  • Picking a library before knowing the state types. Server data still belongs in a query cache.

See it yourself

Wrap a Zustand store with the devtools middleware and open Redux DevTools: you can inspect its state and actions the same way.

Quick quiz

Does Zustand need a Provider?

No. The store is a hook created with create.

What's a derived atom in Jotai?

An atom whose value is computed from other atoms with atom(get => …); it updates when they change.

Why is a module-level store dangerous with SSR?

The server process handles many users; a shared module-level store can leak one request's data into another's.

  • Zustand: create((set) => ({...})), no Provider, read slices useCart(s => s.items.length).
  • Jotai: atoms + derived atoms (atom(get => ...)), re-render only on atoms you read.
  • MobX: makeAutoObservable + observer, mutate directly, spreadsheet-style auto updates.
  • Trap: module-level store on the server (SSR) is shared across requests → user data leaks. Create a store per request, pass via context.
