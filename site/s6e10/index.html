Key points

  • Reconnecting instantly after a server restart makes every client reconnect at once: a thundering herd.
  • Use exponential backoff (1, 2, 4, 8 … capped at 30 s) with random jitter.
  • On reconnect: resync missed messages (since=<last seq>), then flush the outbox of unsent messages. Don't retry closes that won't succeed (like auth failures).

Interview answer

When a socket closes unexpectedly, I reconnect with exponential backoff and jitter so clients don't stampede the server after an outage. Once reconnected, I fetch everything after the last sequence number I processed, then resend any queued outgoing messages. I listen to online, offline and visibilitychange events to reconnect promptly when the network returns, and I use an AbortController to tear down the old socket's listeners and pending catch-up requests. I only retry abnormal closures; a normal close or an authentication failure needs a different response, like re-login.

The analogy

After a power cut, if every house switches every appliance on at the same instant, the grid trips again. Switching on gradually, at slightly different times, lets everyone recover.

How it works

let attempt = 0;
function connect() {
  const ws = new WebSocket(URL);
  ws.onopen = async () => { attempt = 0; await resyncSince(lastSeq); flushOutbox(ws); };
  ws.onclose = e => {
    if (e.code === 1000 || e.code === 4001) return;           // normal close / auth failed: don't retry
    const delay = Math.min(30_000, 1000 * 2 ** attempt++) * (0.5 + Math.random() / 2);
    setTimeout(connect, delay);
  };
}
window.addEventListener('online', () => { attempt = 0; connect(); });

Common traps

  • Instant retries in a tight loop: thundering herd and battery drain.
  • Retrying every close: an expired session needs re-login, not infinite retries.
  • Not resyncing: messages sent while you were disconnected never appear.

See it yourself

WhatsApp Web → turn Wi-Fi off: a "Computer not connected" banner appears. Turn it on: missed messages arrive after a moment.

Quick quiz

Why add jitter to reconnect backoff?

So clients that disconnected at the same moment don't all reconnect at the same moment.

What should happen right after reconnecting?

Fetch missed messages since the last processed sequence number, then resend the outbox.

Which closes shouldn't trigger automatic reconnects?

Normal closes (1000) and auth/permission failures; those need user action instead.

  • AbortController (S5E13): one abort() removes the old socket's listeners and cancels its catch-up fetch.
