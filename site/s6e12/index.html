Acks & dedup

Key points

  • WhatsApp's ticks map to acknowledgements: one grey = the server got it, two grey = delivered to the device, two blue = read. The clock = still pending.
  • If an ack is lost, the client retries and the server may get the message twice.
  • Fix: a client-generated id (crypto.randomUUID()), an outbox until acked, and the server drops repeat ids. At-least-once delivery + dedup ≈ exactly-once.

Interview answer

Reliable messaging is built from acknowledgements and retries. The client gives each outgoing message a unique ID, shows it optimistically with a pending state, keeps it in an outbox and resends it until the server acknowledges it. Because an ack can be lost after the server stored the message, retries can create duplicates, so the server deduplicates by the client ID and the client merges the server's echo with its local copy. The result is at-least-once delivery with deduplication, which behaves like exactly-once. The ID must be generated on the client, because a server ID doesn't exist until the first attempt succeeds.

The analogy

Sending a registered letter with a reference number. If you don't get the receipt, you send it again with the same number, and the post office recognises it's the same letter and doesn't deliver it twice.

How it works

function sendMessage(text) {
  const msg = { id: crypto.randomUUID(), text, status: 'pending' };
  addBubble(msg);                                   // optimistic UI
  outbox.set(msg.id, msg);
  trySend(msg);
}
function onAck({ id, seq }) {
  outbox.delete(id);
  updateBubble(id, { status: 'sent', seq });        // merge own echo by id, not by text
}

Common traps

  • Generating the id on the server. It doesn't exist until the first attempt succeeds, so retries can't be matched.
  • Deduping by message text. Two identical messages ("ok") are different messages.
  • Clearing the outbox on send instead of on ack.

See it yourself

On WhatsApp, send a message in airplane mode: the clock icon stays until you reconnect, then one tick, then two.

Quick quiz

Why can retries create duplicate messages?

The server may have stored the message but the ack was lost, so the client sends it again.

Why must the message id be generated on the client?

So every retry carries the same id, letting the server recognise duplicates before any server id exists.

What does "at-least-once + dedup" achieve?

Messages are never lost (retries) and never shown twice (dedup), effectively exactly-once delivery.

  • Lost ack → retry → duplicate. Fix: client-generated id (crypto.randomUUID()), outbox until acked, server drops repeat ids, client merges its own echo.
