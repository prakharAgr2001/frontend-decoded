Key points

  • Rollback has three steps: onMutate snapshots the previous data and returns it, onError restores it and shows a toast with Retry, onSettled refetches so the server's truth wins.
  • Fast repeated taps (like → unlike → like) can arrive out of order and restore a stale snapshot.
  • Fix: send intent (PUT { liked: true }, idempotent) instead of "toggle", and always settle with a refetch.

Interview answer

For optimistic updates I snapshot the cache in onMutate and return it as context. If the mutation fails, onError writes the snapshot back and shows a message with a retry option. onSettled invalidates the query so the final state always matches the server. To handle rapid toggles, I send the desired end state rather than a toggle, which makes requests idempotent and order-independent, and I can serialize mutations per item. The final refetch corrects any remaining inconsistency.

The analogy

Writing in pencil with an eraser handy. You write the expected answer straight away, keep a note of what was there before, and erase back to it if the teacher says you're wrong. At the end of the class you copy the teacher's final answer.

How it works

Common traps

  • Restoring a stale snapshot after several quick mutations. Settle with a refetch.
  • No user feedback on failure. Always tell users and offer retry.
  • Non-idempotent endpoints. Retrying a "toggle" or "add 1" request can double-apply.

See it yourself

In DevTools → Network set throttling to Slow 3G and block the like endpoint, then tap like repeatedly on your own app: the UI should end in the correct state with an error message.

Quick quiz

What do onMutate, onError and onSettled each do in a rollback?

onMutate snapshots and applies the optimistic update; onError restores the snapshot and notifies; onSettled refetches to sync with the server.

Why send "liked: true" instead of "toggle"?

It's idempotent: repeated or reordered requests always produce the same final state.

Why refetch even after success?

To make sure the cache matches the server, including changes from other users or reordered requests.

  • onMutate: snapshot prev and return it · onError: restore ctx.prev + toast with Retry · onSettled: invalidate (server truth wins).
  • Races: like/unlike/like out of order → stale snapshot. Fix: send intent (PUT { liked: true }, idempotent) not toggle, serialize per item, always settle with a refetch.
