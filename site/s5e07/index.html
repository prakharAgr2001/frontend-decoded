Cursor pagination

Key points

  • Cursor pagination asks for "10 items after this one" instead of "skip 10".
  • The response has items plus an opaque nextCursor; the client sends ?after=<cursor>. nextCursor: null means the end.
  • With an index, page 1000 is about as fast as page 1, and inserts don't cause duplicates.

Interview answer

Cursor pagination returns a pointer to the last item, and the next request asks for items after that pointer, using an indexed WHERE clause instead of OFFSET. Inserts and deletes elsewhere don't shift the window, so there are no duplicates or gaps, and performance stays constant at any depth. To avoid skipping rows that share the same sort value, the cursor includes a unique tiebreaker like (created_at, id). The trade-off is that users can't jump directly to page 50.

The analogy

A bookmark instead of a page number. Even if someone adds pages at the front of the book, your bookmark still sits exactly where you stopped.

How it works

-- Compound cursor (created_at, id) avoids skipping rows with equal timestamps
SELECT * FROM posts
WHERE (created_at, id) < (:cursor_time, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT 10;

// Client with React Query
const { data, fetchNextPage, hasNextPage } = useInfiniteQuery({
  queryKey: ['feed'],
  queryFn: ({ pageParam }) => fetch(`/api/posts?after=${pageParam ?? ''}`).then(r => r.json()),
  initialPageParam: null,
  getNextPageParam: last => last.nextCursor,      // null → no more pages
});

Common traps

  • Ties on the sort key: two posts with the same timestamp → one gets skipped. Use (created_at, id).
  • Exposing raw cursor values that clients start depending on. Encode them (e.g. base64) and treat them as opaque.
  • No jump-to-page. Cursor pagination can't go directly to page 50.

See it yourself

Open https://www.reddit.com/r/javascript.json: the response has "after": "t3_…", a cursor for the next page.

Quick quiz

Why doesn't cursor pagination produce duplicates on new inserts?

It asks for items after a specific item, not after N rows, so new items at the top don't shift the window.

Why include the id in the cursor?

As a tiebreaker for rows with the same timestamp, so none are skipped or repeated.

What can't cursor pagination do easily?

Jump straight to an arbitrary page number.

  • "10 items older than this one": response has items + opaque nextCursor; client sends ?after=<cursor>; null = end.
  • Server: WHERE created_at < :cursor ORDER BY created_at DESC LIMIT 10 — with an index, page 1000 ≈ page 1.
  • See it: reddit.com/r/javascript.json → "after": "t3_…".
  • Trap: ties on the sort key skip rows → sort by (created_at, id) and put both in the cursor. Cost: no jump to page 50.
