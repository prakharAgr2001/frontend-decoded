Key points

  • Making one product page fast follows a fixed order: measure → loading → bundle → hero image → layout shifts → third parties → interactions → budget.
  • Each step targets a specific metric: TTFB/LCP, INP or CLS.
  • Finish with a budget in CI so the gains don't disappear.

Interview answer

I start with field data to see which Core Web Vital fails. For loading, I serve HTML from a CDN with caching, inline critical CSS, defer scripts and preconnect to key origins. I shrink the bundle with route splitting, lazy features and lighter dependencies, compressed with Brotli. The hero image is a responsive AVIF with fetchpriority high. I reserve space for images, ads and fonts to keep CLS low, put third-party scripts behind facades or after interaction, and keep interactions responsive with instant feedback, transitions, virtualization and workers. Then I lock it in with performance budgets in CI.

The analogy

Servicing a car in the right order: check the dashboard warnings first (measure), then the engine (loading), then lose the extra weight (bundle), then the tyres and alignment (images and shifts), and finally set a service schedule (budget) so it doesn't slide back.

How it works

Common traps

  • Optimising without measuring. Fix the metric that's actually failing first.
  • One-off clean-ups. Without budgets, performance regresses within months.
  • Ignoring mobile. Test on a mid-range Android phone on 4G.

See it yourself

Run PageSpeed Insights on any big e-commerce product page and map each failed audit to one of the steps above.

Quick quiz

What's the first step in improving a slow page?

Measure with field data to find which metric is failing, then use lab tools to find the cause.

Three fixes that improve LCP?

Faster TTFB (CDN, caching), discoverable high-priority hero image, smaller properly sized modern image formats, less render-blocking CSS/JS.

How do you keep a page fast after optimising it?

Performance budgets enforced in CI and ongoing real-user monitoring.

  • Measure (CWV, field vs lab) → loading (CDN TTFB, critical CSS, defer, preconnect) → bundle (split, lazy, diet, Brotli) → hero (AVIF srcset, fetchpriority) → shifts (reserve space, font fallback) → third parties (facade, delay) → interactions (feedback first, transition, virtualize, worker, chunking) → budget in CI.
