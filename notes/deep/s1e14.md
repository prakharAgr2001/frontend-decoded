## TL;DR
- JavaScript in the browser runs on **one main thread**: one "chef" who also handles clicks, scrolling, style, layout and paint.
- **Waiting** (timers, network, events) happens outside the chef, in the browser's Web APIs. **Computing** happens on the chef.
- So a `fetch()` never freezes the page, but a long loop does. Anything over ~50 ms on the main thread is a **long task**, and users feel it.

## The analogy
A restaurant with exactly one cook. The cook makes your food, but also takes orders, plates dishes and wipes the counter. If one order takes the cook 3 minutes of chopping, every other table waits, even the person who just wants water.

The cook does have helpers: a timer on the oven, a delivery boy who fetches ingredients. They work on their own and leave a note on the counter when done. The cook reads the notes only when the hands are free.

## How it actually works
The main thread runs one piece of work at a time. Here's the loop it repeats forever:

```loop
Pick the oldest task | a click, a timer that fired, a fetch response…
Run it to the end | on the call stack, no interruptions
Run ALL microtasks | promise callbacks, queueMicrotask
Draw a frame (if it's time) | requestAnimationFrame → style → layout → paint, ~every 16.7 ms
```
Meanwhile the **Web APIs** (timers, network, input) work on their own and drop finished jobs into the task queue.

- **Call stack:** the function the chef is running right now, and the functions that called it.
- **Web APIs:** the helpers. `setTimeout`, `fetch`, DOM events and so on are handled by the browser, not by your JavaScript.
- **Task queue:** finished helper jobs waiting for the chef (a timer fired, a click happened, a response arrived).
- **Rendering:** the browser tries to draw ~60 times a second (every ~16.7 ms), but only *between* tasks. If your task runs 3 seconds, no frames are drawn for 3 seconds. That's the "frozen" page.

### Blocking vs not blocking
```js
// Freezes the page for 3 seconds: the chef never gets a break.
const end = Date.now() + 3000;
while (Date.now() < end) {}

// Doesn't freeze anything: the waiting happens in the browser, not on the chef.
fetch('/api/orders').then(r => r.json()).then(render);
setTimeout(() => console.log('3 seconds later'), 3000);
```

### How to do heavy work without freezing
**1. Break it into chunks** and give the chef a break between them:

```js
async function processAll(items) {
  for (let i = 0; i < items.length; i++) {
    heavyWork(items[i]);
    if (i % 200 === 0) {
      // Let clicks, scroll and paint happen, then continue.
      await new Promise(r => setTimeout(r, 0));
    }
  }
}
```

**2. Hire a second chef** with a Web Worker, which runs on a separate thread (it can't touch the DOM, but it can crunch numbers):

```js
// main.js
const worker = new Worker('worker.js');
worker.postMessage(bigArray);
worker.onmessage = e => showResult(e.data);

// worker.js
onmessage = e => postMessage(expensiveCalculation(e.data));
```

## See it yourself
- Open any site, paste the 3-second `while` loop in the Console, then try to scroll or click. Nothing responds until it ends.
- DevTools → **Performance** → record while it runs. You'll see one long grey/yellow block with a red triangle: a **long task**.

## Real-world connection
Google's **INP** (Interaction to Next Paint) metric, one of the Core Web Vitals, measures exactly this: how long after a tap the page actually paints a response. Busy main threads are the #1 cause of bad INP.

## Common mistakes
- **"`async` makes it run in the background."** It doesn't. An `async` function still runs on the main thread; only the *waiting* (`await fetch`) is offloaded.
- **Thinking `setTimeout(fn, 0)` runs now.** It means "add a task as soon as possible". It still waits for the current task (and all microtasks) to finish.
- **Parsing a huge JSON or sorting 1 lakh rows in a click handler.** Chunk it, move it to a worker, or do it on the server.

## Interview questions
<details><summary>Is JavaScript single-threaded? Then how does fetch not block?</summary>

Your JavaScript runs on one thread, but the browser is multi-threaded. `fetch` hands the request to the browser's network layer; when the response arrives, a callback is queued and runs when the main thread is free.
</details>
<details><summary>What's the output order?</summary>

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('D');
```
**A, D, C, B.** Synchronous code first (A, D). Then all microtasks (the promise: C). Then the next task (the timer: B).
</details>
<details><summary>What is a long task and why does it matter?</summary>

Any task that keeps the main thread busy for more than 50 ms. During it the page can't respond to input or paint, so clicks feel laggy. It directly hurts INP.
</details>
<details><summary>How would you keep the UI responsive while processing a large dataset?</summary>

Split the work into chunks and yield between them (`setTimeout`, or `scheduler.yield()` where supported), move pure computation to a Web Worker, or paginate/virtualise so you don't process everything at once.
</details>
