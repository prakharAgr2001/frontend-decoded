## Key points
- In React, an error thrown during render **with no error boundary unmounts the whole app**: a blank page.
- Wrap each independent widget in an **ErrorBoundary** with a fallback and a Retry button.
- Decide what's **critical** (price, checkout → show an error page) vs **optional** (recommendations → just hide).

## Interview answer
> To avoid one failure taking down the whole page, I isolate widgets with error boundaries that render a fallback and a retry option, and on the data side I use Promise.allSettled so one failed request doesn't discard the others. I classify each part as critical or optional: critical failures like product price get a proper error state, optional ones like recommendations are hidden. Error boundaries only catch errors during rendering, so for event handlers and async code I store the error in state or use the data library's throwOnError option to surface it to the boundary.

## The analogy
A building with fire doors. A fire in one room shouldn't burn down the whole building; the doors contain it, and the rest of the building keeps working.

## How it works
```jsx
import { ErrorBoundary } from 'react-error-boundary';

function ProductPage() {
  return (<>
    <ProductDetails />                                    {/* critical: let the route error page handle it */}
    <ErrorBoundary fallbackRender={({ resetErrorBoundary }) =>
      <p>Reviews couldn't load. <button onClick={resetErrorBoundary}>Retry</button></p>}>
      <Reviews />
    </ErrorBoundary>
    <ErrorBoundary fallback={null}>                       {/* optional: just hide it */}
      <Recommendations />
    </ErrorBoundary>
  </>);
}
```

```compare
Critical || Optional
Price, add to cart, checkout || Recommendations, reviews, ads
Clear error state + retry || Hide quietly or show a small notice
Block the action if data is wrong || Page still works without it
```

## Common traps
- **Error boundaries don't catch** event-handler errors, async errors (setTimeout, promises) or server-side errors. Put the error in state and throw during render, or use `throwOnError`.
- **One boundary around the whole app** still blanks everything.
- **Hiding critical failures** silently, e.g. showing a stale price.

## See it yourself
In a React app, throw an error inside one small component and reload: without a boundary the whole page goes blank; with one, only that widget shows its fallback.

## Quick quiz
<details><summary>What happens to an uncaught render error in React?</summary>

React unmounts the whole component tree, leaving a blank page.
</details>
<details><summary>Which errors don't error boundaries catch?</summary>

Errors in event handlers, async code (timers, promises), server rendering, and the boundary itself.
</details>
<details><summary>How do you handle optional widget failures?</summary>

Wrap them in an error boundary whose fallback hides them or shows a small message.
</details>
