## Key points
- This is a revision episode: four interview questions on **measuring performance**.
- Know the Core Web Vitals thresholds, why lab and field disagree, how to debug a slow LCP, and how to fix a banner causing CLS.

## Interview answer
> I measure with field data first: Core Web Vitals at the 75th percentile, LCP 2.5 s, INP 200 ms, CLS 0.1. Lab tools help me find causes. For each problem I break the metric into parts, like LCP's TTFB, load delay, load time and render delay, and fix the biggest part rather than guessing.

## Quick quiz
<details><summary>What are the Core Web Vitals, their thresholds, and at what percentile?</summary>

LCP ≤ 2.5 s (loading), INP ≤ 200 ms (responsiveness), CLS ≤ 0.1 (visual stability), all assessed at the 75th percentile of real visits, mobile and desktop separately.
</details>
<details><summary>Lighthouse gives 98, but field INP is poor. Why?</summary>

Lighthouse doesn't interact with the page, so it can't measure INP (TBT is only a proxy). It uses one simulated device, while real users run slower phones, have extensions, use the page for minutes and click things. Field data is also a 28-day window, so it may reflect older code.
</details>
<details><summary>The hero image downloads fast, but LCP is still slow. How do you debug it?</summary>

Break LCP into parts. Slow TTFB → server/CDN/caching. Big load delay → the image is discovered late: put it in the HTML as an `<img>`, add `fetchpriority="high"` or a preload, remove lazy loading. Big render delay → render-blocking CSS/JS or client-side rendering is holding the paint.
</details>
<details><summary>A cookie banner causes CLS. What are your options?</summary>

Reserve its space from the first paint, render it as an overlay with `position: fixed` so it doesn't push content, or animate it in with `transform`, which doesn't shift layout.
</details>
