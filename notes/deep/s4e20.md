## Key points
- **Boolean soup**: `isLoading`, `isError`, `isSuccess` = 8 combinations, but only about 4 are valid. Bugs live in the impossible ones.
- Replace them with **one `status`** and explicit **transitions**: which events are allowed in which state.
- Events that aren't allowed in the current state are **ignored**: a second "Pay" click during `submitting` does nothing.

## Interview answer
> Instead of several booleans that can combine into impossible states, I model UI flows as a finite state machine: a single status value and a table of allowed transitions for each event. This makes impossible states unrepresentable and invalid events harmless, for example a submit event is ignored while already submitting. For simple flows a reducer with a status field is enough; for complex flows with nested or parallel states, guards and timers, XState provides a full statechart implementation with visual tooling.

## The analogy
A traffic signal. It can only be red, yellow or green, and it moves through them in a fixed order. It can never be "red and green at the same time", and pressing the pedestrian button during green doesn't break it.

## How it works
```steps
idle | SUBMIT → submitting
submitting | SUCCESS → success, FAIL → error (SUBMIT ignored)
error | RETRY → submitting
success | final state
```

```js
const machine = {
  idle:       { SUBMIT: 'submitting' },
  submitting: { SUCCESS: 'success', FAIL: 'error' },
  error:      { RETRY: 'submitting' },
  success:    {},
};
const transition = (status, event) => machine[status][event] ?? status;   // unknown event → stay

function reducer(state, event) {
  return { ...state, status: transition(state.status, event.type) };
}
```

## Common traps
- **`isLoading && isError` both true** after a forgotten reset: the classic boolean-soup bug.
- **Double payment**: guard with the machine (ignore SUBMIT while submitting), disable the button, and send an **idempotency key** to the server.
- **Using XState for a simple toggle.** A reducer with a status field is often enough.

## Quick quiz
<details><summary>Why are multiple booleans risky for async UI?</summary>

They allow impossible combinations (loading and error at once), which cause bugs that are hard to reproduce.
</details>
<details><summary>How does a state machine prevent double submission?</summary>

In the submitting state there's no transition for SUBMIT, so the event is ignored.
</details>
<details><summary>When would you reach for XState?</summary>

For complex flows with nested or parallel states, guards, delays/timers, or when visualising the flow helps the team.
</details>
