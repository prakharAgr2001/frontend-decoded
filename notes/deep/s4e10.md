## Key points
- Revision episode: interview questions on **Redux and stores**.
- Know Redux's data flow, why RTK can `push`, when to choose context vs Zustand vs Redux, and why a filter selector re-renders.

## Interview answer
> Redux flows one way from dispatched actions through pure reducers to a new state that subscribers render. Redux Toolkit uses Immer so reducers can use mutating syntax safely. I choose context for rarely changing values, a light store like Zustand for shared client state, and Redux Toolkit for large teams that need strict structure, while server data always goes in a query cache.

## Quick quiz
<details><summary>Explain the Redux data flow.</summary>

A component dispatches an action → the reducer computes new state purely → the store saves it and notifies subscribers → components whose selected data changed re-render.
</details>
<details><summary>Why can RTK reducers call push?</summary>

Immer passes a draft; it records the mutations and produces a new immutable state. This only works inside createSlice/createReducer.
</details>
<details><summary>Context vs Zustand vs Redux: when would you use each?</summary>

Context for rarely changing app-wide values (theme, user, locale). Zustand for shared client state with little boilerplate and selector-based subscriptions. Redux Toolkit for large apps and teams wanting strict conventions, middleware and DevTools. Server data in a query cache in all cases.
</details>
<details><summary>A selector filtering a list re-renders on every update. Why and how to fix it?</summary>

It returns a new array each time. Memoize with createSelector or compare with shallow equality.
</details>
