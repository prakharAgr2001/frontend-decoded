## Key points
- **Short polling** = ask the server on a fixed timer: "anything new?"
- Costs: **latency** (up to one interval late) and **load**: 10,000 open tabs polling every 5 s = 2,000 requests per second, mostly empty.
- Fine for **rare updates where a few seconds of delay is OK**: dashboards, build status, unread badges. It works through every proxy.

## Interview answer
> Short polling sends a request at a fixed interval to check for updates. It's the simplest approach, works with any infrastructure and caching, and is perfectly fine for low-frequency updates where some delay is acceptable. The drawbacks are latency up to the interval and a lot of wasted requests at scale. I schedule the next poll after the previous response arrives rather than using setInterval, back off when the server is slow, and pause polling when the tab is hidden.

## The analogy
A kid in the back seat asking "are we there yet?" every five minutes. Simple, but most answers are "no", and you only learn you've arrived up to five minutes late.

## How it works
```js
// setTimeout after the response: no overlapping requests if the server slows down
async function poll() {
  if (!document.hidden) {
    try {
      const res = await fetch('/api/notifications/unread-count');
      updateBadge((await res.json()).count);
    } catch { /* ignore, try again next round */ }
  }
  setTimeout(poll, 5000);
}
poll();
document.addEventListener('visibilitychange', () => { if (!document.hidden) updateNow(); });
```

```compare
setInterval(fetch, 5000) || setTimeout after response
Fires even if the last request is still running || Next poll starts only after the last finishes
Overlapping requests when the server slows || Never overlaps
Responses can arrive out of order || Always in order
```

## Common traps
- **`setInterval` with fetch** overlaps and piles up when the server is slow.
- **Polling hidden tabs** wastes battery and server capacity. Check `document.hidden`.
- **Too short an interval** at scale = huge, mostly empty traffic.

## See it yourself
Open GitHub Actions on a running workflow with DevTools → **Network**: you'll often see status requests repeating on a timer.

## Quick quiz
<details><summary>What's the worst-case delay with 10 s short polling?</summary>

About 10 seconds (just missed the last poll).
</details>
<details><summary>Why use setTimeout instead of setInterval for polling?</summary>

So the next request starts only after the previous one finishes, avoiding overlap and out-of-order responses.
</details>
<details><summary>When is short polling the right choice?</summary>

Low-frequency updates where a few seconds' delay is fine, and simplicity or compatibility matters.
</details>
