## Key points
- **Exponential backoff**: wait 1 s, 2 s, 4 s, 8 s… (with a cap) between retries. Add **jitter** (randomness) so thousands of clients don't retry at the same instant.
- Retry: network errors, timeouts, **429** (after `Retry-After`), **5xx** like 503. **Don't** retry 400, 401 or 404.
- React Query retries queries 3 times by default; mutations 0 times. Retry a POST only with an **idempotency key**.

## Interview answer
> I retry only transient failures: network errors, timeouts, 429 and 5xx responses, never client errors like 400, 401 or 404. Retries use exponential backoff with a maximum delay and random jitter, so a recovering server isn't hit by a synchronized wave of requests, the thundering herd. For 429 I respect the Retry-After header. Reads are safe to retry; writes only when they're idempotent, which for POST means sending an Idempotency-Key the server can use to deduplicate.

## The analogy
Calling a busy friend. You don't redial every second; you wait a bit longer each time. And if everyone in your family calls at exactly the same moments, the line stays jammed, so each person waits a slightly random time.

## How it works
```js
async function fetchWithRetry(url, options = {}, retries = 4) {
  for (let attempt = 0; ; attempt++) {
    try {
      const res = await fetch(url, options);
      if (res.ok) return res;
      const retryable = res.status === 429 || res.status >= 500;
      if (!retryable || attempt >= retries) throw new Error(`HTTP ${res.status}`);
      const retryAfter = Number(res.headers.get('Retry-After')) * 1000;
      await sleep(retryAfter || backoff(attempt));
    } catch (err) {
      if (err.name === 'AbortError' || attempt >= retries) throw err;
      await sleep(backoff(attempt));                         // network error → retry
    }
  }
}
const backoff = n => Math.min(30_000, 1000 * 2 ** n) * (0.5 + Math.random() / 2);  // capped + jitter
const sleep = ms => new Promise(r => setTimeout(r, ms));
```

## Common traps
- **Retrying non-idempotent POSTs** can create duplicate orders or payments.
- **No jitter**: every client retries in sync and knocks the server over again.
- **Retrying 4xx errors**: they won't succeed on retry; fix the request instead.

## Quick quiz
<details><summary>Why add jitter to backoff?</summary>

To spread retries out so many clients don't hit the recovering server at the same moment (thundering herd).
</details>
<details><summary>Which status codes are worth retrying?</summary>

Network errors/timeouts, 408, 429 (after Retry-After), and 5xx like 502/503/504. Not 400, 401, 403 or 404.
</details>
<details><summary>How do you make a POST safe to retry?</summary>

Send an Idempotency-Key so the server recognises and ignores duplicates.
</details>
