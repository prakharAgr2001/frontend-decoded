## TL;DR
- JavaScript frees memory automatically with **garbage collection (GC)**: anything that can no longer be reached from the "roots" (globals, the current stack) is removed.
- A **memory leak** is memory you don't need anymore but that's **still reachable**, so GC can't free it.
- Usual suspects: **listeners not removed, intervals still running, caches that only grow, detached DOM nodes, closures holding big data.**

## Say it in the interview
> JavaScript uses mark-and-sweep garbage collection: starting from roots like the global object and the call stack, it marks everything reachable and frees the rest. A leak happens when something unneeded stays reachable, typically an event listener or interval that's never cleaned up, a global or module-level cache that keeps growing, or a closure or data structure that still references removed DOM nodes. In React I clean up subscriptions and timers in the useEffect cleanup function, and I find leaks by comparing heap snapshots in the Memory panel.

## The analogy
A hotel that checks out guests automatically when nobody has their room key anymore. A leak is a guest who left the city but whose key is still on the reception desk: the room stays booked forever.

## How it works
```steps
Roots | window/globalThis, the current call stack, active timers and listeners
Mark | follow every reference from the roots and mark what's reachable
Sweep | everything not marked is freed
Leak | something you forgot about still points to the old data, so it's always "reachable"
```

```jsx
// ❌ Leaks: interval + listener keep running after the component unmounts
useEffect(() => {
  const id = setInterval(poll, 1000);
  window.addEventListener('resize', onResize);
}, []);

// ✅ Cleanup function removes them
useEffect(() => {
  const id = setInterval(poll, 1000);
  window.addEventListener('resize', onResize);
  return () => {
    clearInterval(id);
    window.removeEventListener('resize', onResize);
  };
}, []);
```

- **Detached DOM nodes:** removed from the page but still referenced from a JS variable or array, so the whole subtree stays in memory.
- `WeakMap`/`WeakRef` hold keys without preventing their collection: handy for caches attached to objects.

## Traps interviewers love
- ⚠️ **"JS has GC, so there are no leaks."** GC only frees *unreachable* memory. Leaks are reachable by mistake.
- ⚠️ **Anonymous listeners can't be removed.** `removeEventListener` needs the exact same function reference.
- ⚠️ **Closures keep their outer variables alive.** A tiny callback can keep a huge array in memory.

## See it yourself
DevTools → **Memory** → take a **heap snapshot**, use the page (open/close a modal 10 times), take another → choose **Comparison**. Filter by "Detached" to find removed DOM nodes that are still held.

## Quick quiz
<details><summary>Why might a removed DOM element still use memory?</summary>

Some JS reference (a variable, array, cache, closure or listener) still points to it, so it's reachable and the GC can't free it: a detached DOM node.
</details>
<details><summary>What should a React useEffect cleanup do?</summary>

Undo everything the effect set up: clear timers, remove listeners, unsubscribe, abort fetches.
</details>
<details><summary>When is a WeakMap useful?</summary>

To associate data with objects (like DOM nodes) without keeping them alive: when the object is gone, its entry can be garbage-collected.
</details>
