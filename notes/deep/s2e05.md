## Key points
- In **static site generation (SSG)**, HTML is built **once, at build time**, then copied to CDN servers worldwide.
- Every visitor gets the same ready-made file, so it's the **fastest and cheapest** option.
- Perfect for content that rarely changes: docs, blogs, marketing pages. Bad on its own for data that changes often.

## Interview answer
> SSG renders pages to HTML during the build step, not per request. Those files are deployed to a CDN and served directly, so TTFB is minimal, there's no server rendering cost, and it scales to any traffic. The limitation is freshness: content only changes when you rebuild and redeploy, and build time grows with the number of pages, so it suits docs, blogs and marketing sites rather than large catalogues with frequently changing data.

## The analogy
Printing newspapers overnight. Everyone in the morning gets an identical copy instantly. But if a price changes at 10 AM, the paper is wrong until tomorrow's print run.

## How it works
```steps
Build | the framework renders every page to HTML once
Deploy | files are uploaded to a CDN
Request | the nearest edge serves the file
No server work | no database calls per visitor
Change content | rebuild + redeploy
```

```jsx
// Next.js: generate one static page per blog post at build time
export async function generateStaticParams() {
  const posts = await getAllPosts();
  return posts.map(p => ({ slug: p.slug }));
}
```

## Common traps
- **50,000 products with hourly price changes.** Builds take too long and data is stale between deploys. Use ISR or SSR for those.
- **Personalised content.** Static HTML is the same for everyone. Add personal bits on the client (e.g. "Hi, Riya").
- **Forgetting it can still be interactive.** Static HTML can hydrate interactive components like any other page.

## See it yourself
Open a docs site (e.g. a Next.js or Astro docs page) → DevTools → **Network** → document → **Headers**: a cache **HIT** and a large `age` value show it was built long before you asked.

## Quick quiz
<details><summary>When is the HTML generated in SSG?</summary>

At build time, once, before any visitor requests the page.
</details>
<details><summary>Why is SSG so fast?</summary>

The page is a pre-built file served from a CDN edge near the user: no server rendering or database work per request.
</details>
<details><summary>What's SSG's main weakness?</summary>

Freshness and build time: content changes require a rebuild, which gets slow with many pages.
</details>
