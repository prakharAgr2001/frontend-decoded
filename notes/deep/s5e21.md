## Key points
- One search page brings Season 5 together: **API → pagination → requests → resilience → loading states**.
- REST endpoint (or BFF) → cursor pagination with infinite scroll → debounce + AbortController → parallel requests, no waterfalls → retries with jitter, dedup, Retry-After → matching skeletons, isolated failures, grouped Suspense.

## Interview answer
> For a search page I'd expose a search endpoint, through a BFF if it aggregates services, with cursor pagination for stable infinite scroll via IntersectionObserver. The input is debounced and each request is aborted when the query changes, so results never go stale. Independent data like filters and suggestions loads in parallel. Transient failures retry with exponential backoff and jitter, respecting Retry-After, and concurrent identical requests are deduplicated by a query cache. Loading uses skeletons matching the result cards, and each section has its own error boundary.

## The analogy
A well-run railway enquiry counter: one window for everything (BFF), answers given page by page without repeats (cursor), stops answering an old question the moment you ask a new one (abort), and politely asks you to wait when it's overloaded (429).

## How it works
```steps
API | GET /search?q=&after= (REST, or a BFF that fans out)
Pagination | cursor + IntersectionObserver infinite scroll
Typing | debounce 300 ms + abort the previous request
Requests | filters, suggestions and results in parallel
Resilience | retry with backoff + jitter, dedupe, respect Retry-After
Loading and errors | matching skeletons, error boundaries, grouped Suspense
```

## Common traps
- **Offset pagination on live results** shows duplicates.
- **No cancellation** lets stale results overwrite new ones.
- **One spinner for the whole page** and one error that blanks everything.

## See it yourself
Search on a big e-commerce site with DevTools → Network open: watch cancelled requests while typing, the cursor parameter on later pages, and parallel requests for filters.

## Quick quiz
<details><summary>Why cursor pagination for search results with infinite scroll?</summary>

Results can change while users scroll; cursors avoid duplicates and gaps and stay fast deep into the list.
</details>
<details><summary>What two techniques together keep a search box correct and efficient?</summary>

Debounce (fewer requests) plus cancelling/ignoring stale requests (no races).
</details>
<details><summary>How should a 429 be handled on the search page?</summary>

Wait for Retry-After, back off, and reduce requests via debounce, dedup and caching.
</details>
