## Key points
- Revision episode: interview questions on **server state**.
- Know server vs client state, `staleTime` vs `gcTime`, how to keep data in sync after mutations, and how to build an optimistic like with rollback.

## Interview answer
> I treat server data as a cached snapshot managed by a server-state library: it caches by key, dedupes, refetches stale data and garbage-collects unused entries. After mutations I invalidate or update the affected keys, and for fast-feeling actions I update optimistically with a snapshot to roll back on error and a refetch to settle.

## Quick quiz
<details><summary>Server state vs client state?</summary>

Server state is owned remotely, async, shared and can go stale (products, orders). Client state is owned by the UI (modal open, theme, draft input).
</details>
<details><summary>staleTime vs gcTime?</summary>

staleTime: how long data is considered fresh, so no automatic refetch. gcTime: how long inactive data stays cached before being removed.
</details>
<details><summary>How do you keep the UI in sync after a mutation?</summary>

Invalidate related queries by key prefix, or write the response with setQueryData; other tabs sync via refetch on focus, BroadcastChannel or server push.
</details>
<details><summary>Walk through an optimistic like with rollback.</summary>

onMutate: cancel queries for that key → snapshot → set the optimistic value → return snapshot. onError: restore snapshot + show an error with retry. onSettled: invalidate to refetch the truth. Send intent (liked: true), not toggle.
</details>
