## Key points
- **Islands architecture:** the page is **static HTML by default**, and only the interactive widgets (a carousel, a cart button) ship JavaScript and hydrate.
- Each island hydrates **independently**, and you choose when: on load, when visible, or when the browser is idle.
- Astro popularised it: `client:load`, `client:visible`, `client:idle`.

## Interview answer
> In islands architecture most of the page is rendered to static HTML with no JavaScript, and only specific interactive components are hydrated as isolated islands. Each island loads its own JS and can be hydrated with different strategies, such as immediately, when idle, or when it scrolls into view using IntersectionObserver. This dramatically cuts JavaScript on content-heavy sites. The trade-off is that islands are separate apps, so sharing state between them needs a shared store or events.

## The analogy
A museum where only a few exhibits are interactive touch screens. Most of the walls are just printed boards (static HTML). You only power the screens people actually use, when they walk up to them.

## How it works
```steps
Render everything to HTML | at build or request time
Mark interactive parts | e.g. <Carousel client:visible />
Ship JS only for islands | the rest of the page has zero JS
Hydrate each island | on load, when idle, or when visible
```

```astro
---
import Header from './Header.astro';      // static, no JS
import Carousel from './Carousel.jsx';
import Newsletter from './Newsletter.jsx';
---
<Header />
<Carousel client:visible />              <!-- hydrates when scrolled into view -->
<Newsletter client:idle />               <!-- hydrates when the browser is idle -->
```

## Common traps
- **Islands can't share React state directly.** Each is its own app. Use a small shared store (e.g. nanostores), custom events, or merge them into one island.
- **Too many islands** each bring their framework runtime overhead.
- **Not a fit for app-like pages** (dashboards) where almost everything is interactive.

## See it yourself
Open an Astro site → DevTools → **Elements**: interactive parts are wrapped in `<astro-island>` tags with their hydration strategy as an attribute.

## Quick quiz
<details><summary>What's the default for content in an islands architecture?</summary>

Static HTML with no JavaScript.
</details>
<details><summary>How does client:visible decide when to hydrate?</summary>

It uses IntersectionObserver and hydrates the island when it enters the viewport.
</details>
<details><summary>Two islands need the same cart count. What are your options?</summary>

A shared store both subscribe to, custom DOM events between them, or combining them into one island.
</details>
