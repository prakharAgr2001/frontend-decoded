## TL;DR
- Computers talk using **IP addresses** (`142.250.183.14`), humans type **names** (`google.com`). DNS turns one into the other.
- Your browser asks a **resolver**, which walks a chain of servers: **root → TLD (.com) → the domain's own name server**.
- Every answer comes with a **TTL** (time to live). Everyone along the way caches it until it expires. That is why DNS is fast most of the time, and why changes take time to reach everyone.

## Say it in the interview
> DNS converts a domain name into an IP address. The browser first checks its own cache and the OS cache, then asks a recursive resolver. On a miss, the resolver asks a root server, then the TLD server like `.com`, then the domain's authoritative name server, and caches the answer for its TTL. For performance I keep third-party domains few and use `dns-prefetch` or `preconnect` for the ones I can't avoid.

## The analogy
Think of your phone's contacts app. You tap "Mom", the phone dials `+91 98xxx xxxxx`. You never remember the number; the app does.

DNS is the contacts app of the internet, except nobody has the full list. So when your browser meets a name it hasn't seen, it has to ask around: first a general directory that knows who handles `.com` names, then the `.com` office that knows who handles `google.com`, then Google's own server that finally says the number.

## How it actually works
When you type `www.example.com` and press Enter, your browser does not go to the internet straight away. It checks the cheapest places first:

1. **Browser cache.** Chrome remembers recent answers for a short while.
2. **Operating system cache** (and the `hosts` file on your laptop).
3. **The recursive resolver.** Usually run by your ISP (Jio, Airtel) or a public one like `8.8.8.8` (Google) or `1.1.1.1` (Cloudflare). This server does the legwork for you.

If the resolver doesn't have the answer cached, it walks the tree:

```chat
Browser -> Resolver: Where is www.example.com?
Resolver -> Root server: Where is www.example.com?
Resolver <- Root server: No idea, but ask the .com servers
Resolver -> .com TLD: Where is www.example.com?
Resolver <- .com TLD: Ask ns1.example.com, it's in charge
Resolver -> ns1.example.com: Where is www.example.com?
Resolver <- ns1.example.com: 93.184.215.14 (keep it for 3600 s)
Browser <- Resolver: 93.184.215.14
note: The resolver caches every answer, so the next lookup skips most of this
```

- **Root servers** know who runs every top-level domain (`.com`, `.in`, `.org`). There are 13 named root server identities, each copied to hundreds of locations worldwide.
- **TLD servers** know which name servers are in charge of each domain under them.
- The **authoritative name server** is the one the domain owner controls (Cloudflare, Route 53, GoDaddy…). It holds the real records.

The resolver remembers every step. The next person asking for any `.com` name skips the root, and anyone asking for `example.com` within the TTL gets an instant answer.

### The records you'll actually meet

| Record | Maps | Example |
|---|---|---|
| `A` | name → IPv4 address | `example.com → 93.184.215.14` |
| `AAAA` | name → IPv6 address | `example.com → 2606:2800:…` |
| `CNAME` | name → another name (alias) | `www.shop.com → shop.netlify.app` |
| `MX` | where email for the domain goes | `→ mail.google.com` |
| `TXT` | free text, used for verification | Google / SPF verification strings |
| `NS` | which servers are authoritative | `→ ns1.cloudflare.com` |

### TTL: the reason "DNS propagation" exists
Each answer says how long it may be cached, for example `TTL 3600` = one hour. If you move your site to a new server and update the `A` record, people whose resolver cached the old answer keep going to the old server until their copy expires. Nothing is "propagating"; old caches are simply timing out.

## Why frontend engineers should care
A DNS lookup on a cold cache costs anything from ~20 ms to a few hundred ms, and it happens **before** a single byte of your page can download. Every new domain your page uses (fonts, analytics, ad scripts, an image CDN) can cost another lookup.

You can tell the browser to start early:

```html
<!-- Look up the name early (cheap) -->
<link rel="dns-prefetch" href="https://fonts.gstatic.com">
<!-- Look up + connect (TCP + TLS) early: use for the 1–3 domains you will definitely hit -->
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
```

## See it yourself
- Terminal: `nslookup google.com` or `dig google.com` (shows the TTL counting down if you run it twice).
- Trace the full walk: `dig +trace google.com`.
- Chrome DevTools → **Network** → click the first request → **Timing** tab → the **DNS Lookup** bar. Reload with cache disabled to see it grow.

## Real-world story
On 4 October 2021, Facebook, Instagram and WhatsApp disappeared for about six hours. A maintenance command cut Facebook's data centers off, and its DNS servers, built to step back when they couldn't reach the data centers, withdrew themselves from the internet. With nobody able to answer "where is facebook.com?", the apps simply couldn't be found. (We made a reel about it: *The day Facebook vanished*.)

## Common mistakes
- **Changing DNS with a long TTL.** Lower the TTL (say to 300 s) a day *before* a migration, switch, then raise it again.
- **Putting a `CNAME` on the root domain** (`example.com` itself). The standard doesn't allow it next to other records; use your provider's `ALIAS`/"CNAME flattening" instead.
- **Assuming DNS is free.** Third-party scripts on five different domains = five lookups on a slow phone network.

## Interview questions
<details><summary>Walk me through what DNS does when I type a URL.</summary>

Browser cache → OS cache/hosts file → recursive resolver. On a miss, the resolver asks a root server (which points to the TLD servers), then the TLD server (which points to the domain's authoritative servers), then the authoritative server, which returns the record with a TTL. Every layer caches the answer.
</details>
<details><summary>Recursive vs iterative queries?</summary>

Your device sends a **recursive** query: "give me the final answer". The resolver then makes **iterative** queries to root, TLD and authoritative servers, each of which only points to the next server.
</details>
<details><summary>Does DNS use UDP or TCP?</summary>

Mostly UDP on port 53, because it's one small question and one small answer. It falls back to TCP for large responses and zone transfers. Newer setups use DNS over HTTPS (DoH) or over TLS (DoT) to encrypt lookups.
</details>
<details><summary>A vs CNAME?</summary>

`A` points a name straight at an IP address. `CNAME` points a name at another name, which then has to be resolved too (an extra step, but you only update one place when the target's IP changes).
</details>
<details><summary>How can a frontend reduce DNS cost?</summary>

Use fewer third-party domains, self-host fonts and critical scripts, and add `dns-prefetch`/`preconnect` for the few domains you can't avoid.
</details>
