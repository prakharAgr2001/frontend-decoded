## Key points
- Every rendering strategy answers one question: **who builds the HTML, and when?**
- **Server-rendered:** the HTML arrives with content, so the browser can paint right away. JS comes later.
- **Client-rendered:** the HTML arrives nearly empty. The browser must download JS, run it, fetch data, *then* paint. Until then: white screen.

## Interview answer
> The core difference between rendering strategies is where and when HTML is produced. With server rendering, the server sends meaningful HTML so the first paint happens as soon as it arrives, and JavaScript hydrates it later. With client rendering, the server sends a shell and a bundle, and the user sees nothing useful until the JS downloads, parses, executes and fetches data. On slow phones that JS cost, not just the network, is often what causes the white screen.

## The analogy
Ordering furniture. **Server-rendered** = it arrives assembled; you can sit on it immediately. **Client-rendered** = a flat-pack box arrives and you must assemble it before anyone can sit. Fast delivery doesn't help if assembly takes ages.

## How it works
```compare
Client-rendered || Server-rendered
Server sends an empty <div id="root"> || Server sends HTML with real content
Download JS bundle || Browser paints immediately
Parse + run JS || Download JS in the background
Fetch data, then render || JS attaches interactivity (hydration)
First paint: late || First paint: early
```

- On a cheap Android phone, parsing and running 1 MB of JS can take several seconds even after it's downloaded.

## Common traps
- **"White screen = slow network."** Often it's the CPU. Throttle the CPU (4x slowdown) in DevTools, not just the network.
- **One strategy for the whole app.** Different pages can use different strategies (later episodes).
- **"Server rendering means no JavaScript."** Usually the same JS still loads to make the page interactive.

## See it yourself
DevTools → **Performance** → tick **Screenshots**, set Network to **Slow 4G** and CPU to **4x slowdown** → reload. The filmstrip shows exactly how long the screen stays white.

## Quick quiz
<details><summary>What question does every rendering strategy answer?</summary>

Who builds the HTML (server or browser) and when (at build time, per request, or after the page loads).
</details>
<details><summary>Why can a client-rendered app show a white screen on a fast network?</summary>

The JS still has to be parsed and executed, then data fetched, before anything renders. On slow CPUs that takes seconds.
</details>
<details><summary>What does server rendering improve, and what doesn't it?</summary>

It improves first paint (content visible sooner). It doesn't remove the JS cost of making the page interactive.
</details>
