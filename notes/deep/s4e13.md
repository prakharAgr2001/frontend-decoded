## Key points
- After a mutation (add, edit, delete), cached data is wrong. **Invalidate** it: `queryClient.invalidateQueries({ queryKey: ['addresses'] })` marks matching queries stale and refetches active ones.
- Query keys work like **folders**: `['addresses']` also matches `['addresses', 7]`. Use `exact: true` for one key.
- Or update the cache directly with **`setQueryData`** using the server's response and skip a round trip.

## Interview answer
> After a mutation succeeds I invalidate the queries whose data it affected. invalidateQueries matches by key prefix, so a hierarchical key structure lets me refresh a whole group, or a single query with exact. When the server returns the updated entity, I can write it straight into the cache with setQueryData to avoid an extra request. Invalidating too little leaves screens showing wrong data, too much refetches everything. Other tabs stay fresh through refetch on window focus, BroadcastChannel or server push.

## The analogy
Crossing out outdated entries in a notebook so you know to recheck them. Label pages by topic so you can cross out "Addresses" in one go instead of hunting for every address entry.

## How it works
```jsx
import { useMutation, useQueryClient } from '@tanstack/react-query';

function useAddAddress() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: addr => fetch('/api/addresses', { method: 'POST', body: JSON.stringify(addr) }).then(r => r.json()),
    onSuccess: saved => {
      qc.setQueryData(['addresses', saved.id], saved);               // write what we already know
      qc.invalidateQueries({ queryKey: ['addresses'] });             // refetch the list(s)
    },
  });
}
```

```compare
invalidateQueries || setQueryData
Marks stale and refetches active queries || Writes data directly into the cache
Always correct (server is the truth) || No extra request
One more round trip || Must match the server's shape exactly
```

## Common traps
- **Too little invalidation**: the list still shows the deleted item.
- **Too much**: invalidating everything after every mutation refetches the world.
- **Other tabs and devices** don't know about your mutation; rely on focus refetch, BroadcastChannel or real-time updates.

## Quick quiz
<details><summary>Does invalidating ['addresses'] affect ['addresses', 7]?</summary>

Yes, matching is by prefix unless you pass `exact: true`.
</details>
<details><summary>When would you use setQueryData instead of invalidating?</summary>

When the mutation response contains the updated data, so you can update the cache without another request.
</details>
<details><summary>How can another open tab learn about the change?</summary>

Refetch on window focus, a BroadcastChannel message between tabs, or server push (WebSockets/SSE).
</details>
