## Key points
- Typing a URL and seeing a page takes **five journeys**: **DNS** (find the server), **TCP** (connect), **TLS** (make it private), **HTTP** (ask for the page), **render** (turn code into pixels).
- The first four are **network** work, mostly waiting. The last one is **browser** work, mostly computing.
- Every speed trick in web performance makes one of these five steps shorter, or skips it.

## Interview answer
> First the browser resolves the domain to an IP using DNS, checking caches before asking a resolver. Then it opens a TCP connection and, for HTTPS, does a TLS handshake to encrypt and verify the server. It sends an HTTP request and gets back HTML. Finally it parses HTML into the DOM and CSS into the CSSOM, builds the render tree, and runs layout, paint and compositing to draw pixels. Subresources like CSS, JS and images trigger the same fetch cycle in parallel.

## The analogy
Ordering food from a new restaurant. You **look up** its number (DNS), **call** and wait for someone to pick up (TCP), **confirm** it's really them and agree on a private line (TLS), **place your order** (HTTP), then the kitchen **cooks** and plates it (rendering). Most of the time is spent waiting, not cooking.

## How it works
```steps
DNS lookup | google.com → 142.250.x.x (cached most of the time)
TCP handshake | SYN → SYN-ACK → ACK, one round trip to open a connection
TLS handshake | agree on encryption keys + check the certificate (1 round trip in TLS 1.3)
HTTP request | GET / → server sends back the HTML
Render | HTML → DOM, CSS → CSSOM → layout → paint → composite → pixels
```

- Steps 1–3 happen **once per connection**, not per file. That's why reusing connections (keep-alive, HTTP/2) matters so much.
- While parsing the HTML, the browser finds `<link>`, `<script>` and `<img>` tags and fetches them too, often in parallel.
- Each round trip costs real time. India to a US server is roughly 200 ms there and back, so 3 round trips = over half a second before the first byte.

## Common traps
- **"DNS happens on every visit."** Usually not. Browser, OS and resolver caches answer most lookups instantly. The first visit is the slowest.
- **"The page appears when the HTML arrives."** No. CSS blocks rendering and synchronous scripts block parsing, so the page waits for them too.
- **Forgetting it repeats.** Every CSS, JS, image and font file goes through fetch again (minus DNS/TCP/TLS if the connection is reused).

## See it yourself
DevTools → **Network** → reload → click the first request → **Timing** tab. You'll see each phase: DNS Lookup, Initial connection, SSL, Waiting (server time), Content Download.

## Quick quiz
<details><summary>Which of the five steps can a CDN shorten?</summary>

TCP, TLS and HTTP: the server is physically closer, so every round trip is shorter. It can also serve cached files without waiting for the origin.
</details>
<details><summary>Why is the first visit to a site slower than the second?</summary>

Nothing is cached yet: DNS answer, connection, and files (HTML/CSS/JS/images) all have to be fetched. On repeat visits the browser cache and connection reuse skip much of it.
</details>
<details><summary>What does "Waiting (TTFB)" in DevTools measure?</summary>

Time to First Byte: from sending the request until the first byte of the response arrives, which is mostly server processing plus one round trip.
</details>
