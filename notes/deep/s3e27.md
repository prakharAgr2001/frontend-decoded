## Key points
- A React component re-renders when: its **state changes**, a **context** it uses changes, or its **parent re-renders**.
- "Props changed" is **not** the trigger: by default children re-render whenever the parent does.
- **Render ≠ DOM update.** React only commits the real differences to the DOM.

## Interview answer
> A component re-renders when its own state updates, when a context value it consumes changes, or when its parent re-renders, regardless of whether props changed, unless it's memoized. Rendering just means calling the component function to produce a new element tree; React then diffs it and commits only actual changes to the DOM. To reduce unnecessary renders I fix the structure first: move state down to where it's used, or pass expensive children as props so they aren't re-created, and use memoization only where profiling shows it helps.

## The analogy
A teacher who asks the whole class to redo their homework whenever one student changes their answer. Most students hand in the same work again (render), and only the changed answer gets updated on the board (DOM commit).

## How it works
```steps
setState in Parent | Parent re-renders
All children re-render too | even if their props are identical
React diffs the output | compares old and new trees
Commit | only real differences touch the DOM
```

```jsx
// Problem: typing re-renders the expensive chart
function Page() {
  const [text, setText] = useState('');
  return (<>
    <input value={text} onChange={e => setText(e.target.value)} />
    <ExpensiveChart />
  </>);
}

// Fix: move the state down into its own component
function SearchBox() {
  const [text, setText] = useState('');
  return <input value={text} onChange={e => setText(e.target.value)} />;
}
function Page() { return (<><SearchBox /><ExpensiveChart /></>); }
```

## Common traps
- **Setting state to an equal value**: React bails out using `Object.is`. But a new object with the same contents is a different value and re-renders.
- **"Re-render means the DOM was rebuilt."** No, renders are cheap until they're frequent or the component is heavy.
- **Context with a big object** re-renders every consumer on any change.

## See it yourself
React DevTools → ⚙ → tick **Highlight updates when components render**. Then use the **Profiler** → "Why did this render?" to see the cause for each component.

## Quick quiz
<details><summary>What are the three causes of a re-render?</summary>

Its own state changes, a consumed context changes, or its parent re-renders.
</details>
<details><summary>Does a child re-render if its props didn't change?</summary>

Yes, when its parent re-renders, unless the child is wrapped in React.memo.
</details>
<details><summary>setCount(5) when count is already 5: re-render?</summary>

No. React bails out because Object.is(5, 5) is true.
</details>
