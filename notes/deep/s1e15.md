## TL;DR
- The **call stack** is where JavaScript runs code *right now*, one function at a time.
- Timers, clicks and network replies don't run immediately. They wait in the **task queue**.
- The **event loop** moves the next task onto the stack **only when the stack is empty**. That's why `setTimeout(fn, 0)` still runs *after* your normal code.

## Say it in the interview
> JavaScript executes synchronous code on the call stack. Async callbacks like timers and events are handled by the browser and, when ready, placed in the task queue. The event loop checks whether the call stack is empty, and only then pushes the next task onto it. So `setTimeout(fn, 0)` doesn't mean "now", it means "after the current code finishes".

## The analogy
A chef with one to-do list. The **stack** is the dish in the chef's hands. The **queue** is the line of order slips on the counter. The chef never drops a half-made dish to read a new slip. Finish this one, then take the next slip.

## How it works
```steps
Run sync code | each function call is pushed onto the stack and popped when it returns
Hand off async work | setTimeout, fetch, click listeners → browser Web APIs, off the stack
Queue the callback | when the timer fires or the response arrives, the callback joins the task queue
Stack empty? Take the next task | the event loop moves one task onto the stack, and repeats
```

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
console.log('C');
// Output: A, C, B
```

A runs, the timer is handed to the browser, C runs. The stack is now empty, so the loop picks up the timer's callback: B.

## Traps interviewers love
- ⚠️ **"0 ms means instant."** It means "queue it as soon as possible", and it still waits for the stack to empty. Deeply nested timers are even clamped to at least 4 ms.
- ⚠️ **A slow function delays every timer.** If the stack is busy for 2 seconds, a timer set for 100 ms fires after about 2 seconds.
- ⚠️ **Stack overflow is a different problem.** Infinite recursion fills the *stack* ("Maximum call stack size exceeded"). It has nothing to do with the queue.

## See it yourself
DevTools → **Sources** → add a breakpoint inside a function → the **Call Stack** panel on the right shows every function waiting to return.

## Quick quiz
<details><summary>What's the output?</summary>

```js
setTimeout(() => console.log(1), 0);
for (let i = 0; i < 1e9; i++) {}
console.log(2);
```
`2`, then `1`. The loop blocks the stack, so the timer's callback waits in the queue until the loop and `console.log(2)` are done.
</details>
<details><summary>Who decides when a queued callback runs?</summary>

The event loop. It runs one when the call stack is empty.
</details>
<details><summary>Where does the timer actually count down?</summary>

In the browser's Web APIs, not in JavaScript. JavaScript just gets a callback in the queue when the time is up.
</details>
