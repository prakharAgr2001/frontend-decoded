## Key points
- Revision episode: interview questions on **API design**.
- Know which methods are idempotent and why retries care, the GraphQL N+1 problem, when to add a BFF, and when not to use GraphQL.

## Interview answer
> I design APIs around the clients: REST for broad, cacheable access, GraphQL for flexible screen-specific data, and a BFF when one screen needs data from many services. I care about idempotency so retries are safe, and I watch for N+1 query patterns.

## Quick quiz
<details><summary>Which HTTP methods are idempotent, and why does it matter?</summary>

GET, PUT, DELETE (POST no, PATCH not guaranteed). Idempotent requests can be retried safely after a timeout; POSTs need an Idempotency-Key header so the server can recognise duplicates.
</details>
<details><summary>What's the GraphQL N+1 problem and the fix?</summary>

One query loads N posts, then the author resolver runs once per post = N more queries. Batch them with DataLoader so all authors load in one query.
</details>
<details><summary>A mobile screen needs data from 4 services. What do you build?</summary>

A BFF endpoint that calls the 4 services in parallel and returns one screen-shaped response.
</details>
<details><summary>When would you not choose GraphQL?</summary>

When CDN/HTTP caching is critical, the API is simple CRUD, or one TypeScript team owns both ends (tRPC fits better).
</details>
