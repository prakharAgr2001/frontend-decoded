## Key points
- A **Web Worker** runs JavaScript on **another thread**, so heavy work doesn't freeze the page.
- Workers **can't touch the DOM**. They talk to the page with `postMessage` and `onmessage`.
- Good for parsing big files, image processing, search indexes, encryption, diffing.

## Interview answer
> Web Workers run scripts in a background thread with their own event loop. They can't access the DOM, but they can do CPU-heavy work like parsing, compression, image manipulation or building search indexes, and communicate with the main thread through postMessage. Messages are copied using structured cloning, which is expensive for large data, so for big binary data I transfer ownership of ArrayBuffers instead of copying. This keeps the main thread free for input and rendering.

## The analogy
Hiring a second chef who works in a back kitchen. They can't serve customers (no DOM), but they can do all the heavy chopping and send the results out through a window.

## How it works
```steps
Create | new Worker(new URL('./worker.js', import.meta.url), { type: 'module' })
Send work | worker.postMessage(data)
Worker computes | on its own thread
Send result back | postMessage(result) → main thread's onmessage
```

```js
// main.js
const worker = new Worker(new URL('./search-worker.js', import.meta.url), { type: 'module' });
worker.postMessage({ type: 'build', items });
input.addEventListener('input', e => worker.postMessage({ type: 'query', q: e.target.value }));
worker.onmessage = e => renderResults(e.data);

// search-worker.js
let index = [];
onmessage = ({ data }) => {
  if (data.type === 'build') index = data.items.map(i => ({ ...i, key: i.name.toLowerCase() }));
  if (data.type === 'query') postMessage(index.filter(i => i.key.includes(data.q.toLowerCase())).slice(0, 50));
};
```

## Common traps
- **Copying huge data.** postMessage clones by default; transfer ArrayBuffers: `postMessage(buf, [buf])`.
- **Trying to update the DOM from a worker.** Send results back and let the main thread render.
- **Using a worker for tiny tasks.** Message overhead can cost more than the work itself.

## See it yourself
DevTools → **Performance** → record while the worker runs: it appears on its own **Worker** track, separate from the Main track.

## Quick quiz
<details><summary>Can a Web Worker read document.querySelector?</summary>

No. Workers have no access to the DOM.
</details>
<details><summary>How do you send a large ArrayBuffer without copying it?</summary>

Pass it in the transfer list: `worker.postMessage(buf, [buf])`. Ownership moves to the worker.
</details>
<details><summary>What kinds of work suit a worker?</summary>

CPU-heavy, DOM-free work: parsing, compression, image processing, search indexing, crypto, diffing.
</details>
