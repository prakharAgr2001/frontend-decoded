## Key points
- **GraphQL** has **one endpoint** (`POST /graphql`). You send a query **shaped like the answer you want**, and the response mirrors it.
- A **schema** defines all types and fields. It fixes **over-fetching** (too much data per call) and **under-fetching** (too many calls).
- Costs: no free HTTP/CDN caching (one URL, POST), and deeply nested queries can be expensive. Errors often come back as **200 OK with an `errors` array**.

## Interview answer
> GraphQL exposes a typed schema through a single endpoint, and clients send queries specifying exactly the fields and nested relations they need, so one request returns exactly that shape. It solves over-fetching and under-fetching and lets different screens evolve independently. The trade-offs are that standard HTTP caching doesn't work out of the box since queries are POSTed to one URL, expensive nested queries need depth and complexity limits or persisted queries, and errors are often returned in an errors array with a 200 status, so clients must check for them.

## The analogy
A buffet versus a set meal. REST endpoints are set meals: you get the whole plate even if you only wanted the dal. GraphQL is a buffet: you take exactly what you want, in one trip.

## How it works
```graphql
query ProfileScreen {
  user(id: 42) {
    name
    avatarUrl
    posts(first: 3) { title likes }
  }
}
```

```json
{ "data": { "user": { "name": "Riya", "avatarUrl": "…",
  "posts": [{ "title": "Hello", "likes": 12 }] } } }
```

```js
const res = await fetch('/graphql', {
  method: 'POST', headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ query, variables: { id: 42 } }),
});
const { data, errors } = await res.json();
if (errors?.length) throw new Error(errors[0].message);   // 200 OK can still contain errors
```

## Common traps
- **Ignoring the `errors` array** because the status was 200.
- **Unbounded nested queries** (friends of friends of friends) can overload the server. Add depth and complexity limits.
- **"GraphQL is faster."** It saves round trips, but careless queries can be slow, and caching takes more work.

## See it yourself
Open instagram.com → DevTools → **Network** → filter `graphql`: requests carry a query (or query id) and variables, and responses mirror the requested shape.

## Quick quiz
<details><summary>What problems does GraphQL solve?</summary>

Over-fetching (getting fields you don't need) and under-fetching (needing several requests for one screen).
</details>
<details><summary>Why is CDN caching harder with GraphQL?</summary>

Queries are usually POSTs to a single URL, so the URL doesn't identify the data. Persisted queries over GET help.
</details>
<details><summary>A GraphQL response is 200 OK. Did it succeed?</summary>

Not necessarily. Check the errors array; partial data with errors is common.
</details>
