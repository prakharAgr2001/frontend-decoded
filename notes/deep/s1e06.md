## Key points
- A **CDN** (Content Delivery Network) keeps **copies of your files on servers close to users** ("edges").
- **Cache hit:** the edge already has the file, so it's fast. **Cache miss:** the edge fetches it once from your server (the "origin"), then serves everyone nearby.
- The real win is **distance**: fewer milliseconds per round trip, and your origin doesn't melt under traffic.

## Interview answer
> A CDN is a network of edge servers around the world that cache copies of content close to users. A request goes to the nearest edge. On a hit, it's served directly with low latency; on a miss, the edge fetches from the origin, caches it based on the Cache-Control headers, and serves it. This reduces latency and offloads the origin. The main challenge is invalidation, which is usually solved with content-hashed filenames and long cache lifetimes, plus purges for HTML.

## The analogy
A pizza chain. Instead of one kitchen in Mumbai delivering to all of India, there's an outlet in every city. Your order goes to the nearest outlet. If it doesn't have the topping, it gets it from the central warehouse once, then keeps it for the next customer.

## How it works
```steps
You request app.js | DNS sends you to the nearest edge (e.g. Bengaluru, not Virginia)
Edge checks its cache | HIT → sent back in a few ms
On a MISS | edge fetches from your origin once
Edge stores it | for as long as Cache-Control allows
Next user nearby | gets a HIT
```

```http
# Static assets with a content hash in the name: cache "forever"
Cache-Control: public, max-age=31536000, immutable      → app.3f9a1c.js

# HTML: always check for a newer version
Cache-Control: no-cache                                   → index.html
```

- CDNs also terminate TLS close to the user, so the handshakes are shorter too.
- Response headers like `x-cache: HIT`, `cf-cache-status: HIT` and `age: 1200` tell you whether you got a cached copy.

## Common traps
- **"Users see the old version after deploy."** Classic cache-invalidation bug. Fix: hashed filenames (`app.3f9a1c.js`) for assets, `no-cache` for HTML, and purge on deploy.
- **Caching personalized pages.** If a response depends on cookies or login, a shared CDN cache can show one user's page to another. Use `Cache-Control: private` or vary correctly.
- **Single point of failure.** If the CDN breaks, every site on it breaks (see the Fastly outage in our reels).

## See it yourself
DevTools → **Network** → click a JS or image file → **Headers** → look for `x-cache`, `cf-cache-status` or `age`. Reload a few times and watch MISS turn into HIT.

## Quick quiz
<details><summary>What's the difference between a cache hit and a miss at the edge?</summary>

Hit: the edge already has a fresh copy and responds immediately. Miss: it has to fetch from the origin first (slower), then caches the result for later requests.
</details>
<details><summary>How do you deploy new JS without users getting stale files from the CDN?</summary>

Put a content hash in the filename so every change is a new URL, cache those for a year with `immutable`, and keep HTML short-lived or `no-cache` so it always points to the latest hashed files.
</details>
<details><summary>Can a CDN help dynamic, non-cacheable pages?</summary>

Yes: shorter TLS/TCP handshakes to a nearby edge, optimized connections from edge to origin, compression, and edge compute. But the biggest wins are for cacheable static content.
</details>
