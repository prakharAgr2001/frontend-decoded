## Key points
- **Resumability** (from the Qwik framework) skips hydration completely.
- The server **serialises the app's state and event wiring into the HTML**. The browser **resumes** where the server stopped, without re-running components.
- Event handlers are tiny chunks loaded **only when the user interacts**.

## Interview answer
> Hydration has to re-execute components on the client to rebuild state and attach listeners. Resumability avoids that: the server serializes application state and the location of each event handler into the HTML, and a tiny global listener on the client loads and runs only the specific handler chunk when an interaction occurs. Startup JavaScript is close to zero regardless of app size. The trade-off is that the first interaction may need to fetch code, so frameworks prefetch likely handlers.

## The analogy
Pausing a video game and saving to a memory card. Resuming loads you right back to the same spot. You don't replay the whole level to get there, which is what hydration does.

## How it works
```compare
Hydration || Resumability
Download all component code || Download almost nothing upfront
Re-run components to rebuild state || State is already in the HTML
Attach every listener || One global listener
Then interactive || Load the handler only when clicked
```

```html
<!-- Qwik output: the handler is a reference to a small lazy-loaded chunk -->
<button on:click="q-chunk-abc.js#s_onClickHandler">Add to cart</button>
```

## Common traps
- **First click can be slow on a bad network** because the handler code is fetched then. Prefetching (Qwik does this with a service worker) mitigates it.
- **Serialization limits:** state must be serializable to go into the HTML.
- **It's not "no JavaScript".** JS still runs; it's just loaded lazily, piece by piece.

## See it yourself
Open a Qwik demo site → DevTools → **Network** (JS filter) → load the page: very little JS. Click a button and watch a small chunk load at that moment.
