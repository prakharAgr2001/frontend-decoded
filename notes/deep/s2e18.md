## Key points
- **Edge rendering** runs your server-side rendering in **many small data centers close to users** (the same places CDNs live).
- Edge runtimes are **lighter than Node**: limited APIs, memory and CPU time.
- Great for **personalisation, redirects, A/B tests and auth checks**. Useless if every render must query a database on the other side of the world.

## Interview answer
> Edge rendering executes server code in globally distributed locations near the user, typically on lightweight runtimes based on web standards rather than full Node.js. That cuts network latency for the request itself, which is great for redirects, geolocation, A/B testing, authentication and personalised responses. But if the edge function needs data from a database in a single region, every query travels back to that region, so the latency savings disappear. It works best with cached, replicated or edge-friendly data.

## The analogy
Opening small kitchens in every neighbourhood. Delivery is faster, unless every kitchen still has to phone the central warehouse in another city for each ingredient.

## How it works
```compare
Single-region server || Edge
Request travels to one region (e.g. US) || Request handled near the user (e.g. Mumbai)
Full Node.js, big memory || Light runtime, small limits
Close to the database || Far from the database (unless data is replicated)
Good for heavy rendering || Good for fast, light logic
```

```js
// Next.js middleware runs at the edge: redirect by country before rendering
export function middleware(req) {
  const country = req.geo?.country;
  if (country === 'IN' && !req.nextUrl.pathname.startsWith('/in')) {
    return Response.redirect(new URL('/in' + req.nextUrl.pathname, req.url));
  }
}
```

## Common traps
- **Edge function + far database = slower, not faster.** Several sequential queries each cross the globe.
- **Node APIs missing.** Some libraries (native modules, `fs`) don't work in edge runtimes.
- **Cold starts and limits** vary by provider; heavy rendering may hit CPU time caps.

## See it yourself
On a site deployed on Vercel or Cloudflare, check response headers like `x-vercel-id` or `cf-ray`: they include the edge location code that served you (e.g. `bom` for Mumbai).

## Quick quiz
<details><summary>What does edge rendering mainly reduce?</summary>

Network latency between the user and the code handling their request.
</details>
<details><summary>When can edge rendering make a page slower?</summary>

When the render needs data from a database in one far-away region, so each query adds a long round trip.
</details>
<details><summary>Give three good edge use cases.</summary>

Redirects and rewrites, A/B test bucketing, auth/session checks, geolocation-based personalisation.
</details>
