## Key points
- There are two queues. **Tasks** (macrotasks): `setTimeout`, `setInterval`, clicks, network events. **Microtasks**: promise `.then`/`await` continuations, `queueMicrotask`.
- After **every task**, the browser runs **all** microtasks, including new ones added along the way, **before** it renders or takes the next task.
- So promises always beat timers.

## Interview answer
> The event loop takes one task from the task queue and runs it. As soon as the call stack is empty, it drains the entire microtask queue, which holds promise reactions and queueMicrotask callbacks, including any microtasks queued during that drain. Only then can it render and move to the next task. That's why a resolved promise's then runs before a setTimeout of 0, and why an endless chain of microtasks can freeze the page.

## The analogy
A doctor's clinic. **Tasks** are patients in the waiting room, seen one at a time. **Microtasks** are "one quick follow-up question" from the patient who's already in the room. The doctor answers *all* follow-ups before calling the next patient, even follow-ups to follow-ups.

## How it works
```loop
Take ONE task | e.g. a timer callback or a click handler
Run it to the end | the call stack is empty again
Drain ALL microtasks | promise callbacks, await continuations, new ones added along the way
Maybe render | if a frame is due: rAF → style → layout → paint
```

```js
console.log(1);
setTimeout(() => console.log(2), 0);          // task
Promise.resolve().then(() => console.log(3)); // microtask
console.log(4);
// Output: 1, 4, 3, 2
```

1 and 4 are synchronous. Then the microtask (3) runs, then the next task: the timer (2).

## Common traps
- **`await` = microtask.** The code *after* an `await` continues as a microtask, not right away.
- **Microtask starvation.** A promise callback that keeps queueing another microtask never lets the browser render or handle clicks. The page freezes.
- **Order puzzle classic:** sync code → microtasks → one task → microtasks → render → next task.

## See it yourself
Paste the code above in the Console. Then try this to watch a timer get starved:
```js
setTimeout(() => console.log('timer'), 0);
let n = 0;
function loop() { if (n++ < 1e6) queueMicrotask(loop); else console.log('done'); }
loop();   // 'done' prints before 'timer'
```

## Quick quiz
<details><summary>What's the output?</summary>

```js
setTimeout(() => console.log('A'), 0);
Promise.resolve().then(() => {
  console.log('B');
  Promise.resolve().then(() => console.log('C'));
});
console.log('D');
```
`D, B, C, A`. The new microtask C is queued during the drain, so it runs before the timer.
</details>
<details><summary>Is the callback of an async function after `await` a task or a microtask?</summary>

A microtask: the continuation after `await` is scheduled like a promise `.then`.
</details>
<details><summary>Can microtasks block rendering?</summary>

Yes. Rendering only happens after the microtask queue is empty, so an endless microtask loop blocks paint and input.
</details>
