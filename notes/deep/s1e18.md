## Key points
- A **long task** is anything that keeps the main thread busy for **more than 50 ms**.
- During a long task the page can't respond to taps or draw, so clicks feel laggy.
- It's measured by **INP** (Interaction to Next Paint), a Core Web Vital since 2024 (it replaced FID). Fix: **break the work up and yield**.

## Interview answer
> A long task is any main-thread task over 50 ms. While it runs, input events and rendering wait, so the UI feels unresponsive, which shows up as poor INP. The 50 ms limit comes from aiming for a response within about 100 ms, leaving time for the browser to handle the input and paint. To fix it, I split the work into smaller chunks and yield back to the browser between them, move heavy computation to a Web Worker, or avoid doing the work at all with pagination or virtualisation.

## The analogy
A single checkout counter. One customer with 300 items (a long task) holds up everyone behind them, even the person buying only water. Splitting the order into baskets lets the cashier serve quick customers in between.

## How it works
```compare
One long task || Chunked with yields
400 ms of work in one go || 8 chunks of 50 ms
Tap during it waits up to 400 ms || Tap waits at most ~50 ms
No frames painted || Frames painted between chunks
Poor INP || Good INP
```

```js
async function processRows(rows) {
  for (let i = 0; i < rows.length; i++) {
    process(rows[i]);
    if (i % 100 === 0) await yieldToBrowser();
  }
}

function yieldToBrowser() {
  // scheduler.yield() keeps your place in line (Chromium); setTimeout is the fallback
  return globalThis.scheduler?.yield ? scheduler.yield() : new Promise(r => setTimeout(r, 0));
}
```

## Common traps
- **"Async functions don't block."** The code between `await`s still runs on the main thread. Only the waiting is offloaded.
- **INP vs FID.** FID measured only the *delay* before the first input was handled. INP measures the *whole* response (delay + processing + next paint) for interactions throughout the visit.
- **Huge React renders count too.** A state update that re-renders 5,000 rows is a long task: memoise, virtualise, or use transitions.

## See it yourself
DevTools → **Performance** → record while clicking around. Long tasks have a **red triangle** in the corner. The **Interactions** track shows how long each tap took to paint.

## Quick quiz
<details><summary>What counts as a long task?</summary>

Any task that occupies the main thread for more than 50 ms.
</details>
<details><summary>What does INP measure?</summary>

The time from a user interaction (tap, click, keypress) until the next frame is painted, reported as roughly the worst interaction during the page visit. Good is 200 ms or less.
</details>
<details><summary>Three ways to fix a long task?</summary>

Chunk and yield (setTimeout / scheduler.yield), move work to a Web Worker, or reduce the work (virtualise lists, debounce, do it on the server).
</details>
