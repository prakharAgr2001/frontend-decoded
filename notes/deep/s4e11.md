## Key points
- **Server state** lives on a server; you only hold a **copy**, and other people can change the original at any time. It can be **stale the moment it arrives**.
- It's async, can fail, and is shared across users and tabs.
- It needs caching, deduplication, refetching when stale, background updates, pagination and garbage collection: jobs that `useEffect` + `useState` don't do.

## Interview answer
> Server state is data owned by the backend, such as products, orders or comments. The client holds a snapshot that can go stale, loading is asynchronous and can fail, and the same data is often needed by many components. Fetching it with useEffect and useState gives no caching, duplicate requests and race conditions. A server-state library like React Query or SWR caches by key, dedupes requests, refetches stale data in the background and garbage-collects unused data. Server Components can remove the client copy entirely for read-only data.

## The analogy
A photo of a railway departure board. It was correct when you took it, but trains keep moving. To trust it, you need to know how old the photo is and retake it when it's too old.

## How it works
```compare
useEffect + useState || Server-state cache
Each component fetches on its own || One request per key, shared (deduped)
No cache: every mount refetches || Cached, instant on revisit
Race conditions on fast changes || Handles cancellation and ordering
Manual loading / error flags || isPending, error, refetch built in
Never refreshes stale data || Refetch on focus, reconnect, interval
```

```jsx
// The useEffect version and its problems
useEffect(() => {
  let ignore = false;                                   // you have to handle races yourself
  fetch(`/api/orders?page=${page}`).then(r => r.json()).then(d => { if (!ignore) setOrders(d); });
  return () => { ignore = true; };
}, [page]);
```

## Common traps
- **Copying server data into Redux/Context** and hand-writing caching logic.
- **Treating fetched data as the truth forever.** It's a snapshot; decide when it's stale.
- **Race conditions**: an older request finishing last overwrites newer data.

## See it yourself
Open the same page in two tabs, change data in one (e.g. rename an item), switch to the other. If it still shows the old value, that's stale server state.

## Quick quiz
<details><summary>What makes server state different from client state?</summary>

It's owned remotely, can change without you knowing, is async and can fail, and is shared across users and components.
</details>
<details><summary>Name three things a server-state library does that useEffect doesn't.</summary>

Caching by key, request deduplication, background refetching of stale data (also retries, garbage collection, pagination helpers).
</details>
<details><summary>When can Server Components replace a client cache?</summary>

For read-only data that doesn't need client-side interactivity or live updates.
</details>
