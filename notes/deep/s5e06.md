## Key points
- **Offset pagination**: `?limit=10&offset=10` → `LIMIT 10 OFFSET 10`.
- If a new item is added at the top while you're reading, everything shifts down and you see **duplicates**. If an item is deleted, you **skip** one.
- Deep offsets are slow: the database still reads and throws away every skipped row.

## Interview answer
> Offset pagination asks for a number of rows after skipping N rows. On a list that changes while the user pages through it, inserts at the top shift rows down so page 2 repeats items from page 1, and deletes shift rows up so items are skipped. Performance also degrades with deep offsets because the database must scan and discard all skipped rows. Offsets are fine for mostly static data or admin tables that need jump-to-page, but feeds should use cursor pagination.

## The analogy
Reading page 2 of a notice board while someone pins a new notice at the very top. Everything slides down one spot, and the first notice on "page 2" is one you already read on page 1.

## How it works
```steps
Load page 1 | items 1–10
A new post arrives at the top | old item 10 becomes item 11
Load page 2 (offset 10) | starts with item 11, which you already saw
Result | a duplicate in the feed
```

```sql
-- Page 1000 still makes the database walk past 9,990 rows
SELECT * FROM posts ORDER BY created_at DESC LIMIT 10 OFFSET 9990;
```

## Common traps
- **Fast-changing feeds** (social, chat, notifications) get duplicates and gaps.
- **Deep pages get slower and slower.**
- **Offset isn't always wrong**: admin tables, search results and "jump to page 7" UIs often need it.

## See it yourself
Paginate a list with offsets in your app, insert a row at the top between page 1 and page 2, and compare the first item of page 2 with the last of page 1.
