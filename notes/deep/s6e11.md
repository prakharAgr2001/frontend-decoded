## Key points
- One socket keeps TCP order. But with **many paths** (several devices, reconnects, HTTP plus socket), **order isn't guaranteed**, and sender clocks can be wrong.
- The server assigns a **sequence number per chat**. The client drops anything with `seq <= last`, buffers gaps, and fetches missing ranges.
- An `async` message handler can finish message 2 before message 1. **Queue and process one at a time.**

## Interview answer
> Within a single TCP connection messages arrive in order, but across reconnections, devices or mixed transports they can be duplicated, delayed or reordered, and device clocks aren't reliable for ordering. So the server assigns a monotonically increasing sequence number per conversation. The client applies messages strictly in sequence: it ignores anything at or below the last applied number, buffers messages that arrive ahead of a gap, and fetches the missing range. If processing is asynchronous, such as decryption, I run messages through a queue so they're applied in order.

## The analogy
Numbered tickets at a bakery counter. Even if people arrive out of breath in a different order, the counter serves 41, then 42, then 43. If 42 hasn't shown up, 43 waits a moment.

## How it works
```steps
Message arrives with seq | e.g. 43
seq ≤ lastApplied? | duplicate → drop it
seq = lastApplied + 1? | apply it, then apply any buffered next ones
seq > lastApplied + 1? | gap → buffer it and fetch the missing range
```

```js
let last = 0; const buffer = new Map(); let chain = Promise.resolve();

function onMessage(msg) {
  chain = chain.then(() => handle(msg));                 // process strictly one at a time
}
async function handle(msg) {
  if (msg.seq <= last) return;                           // duplicate
  if (msg.seq > last + 1) { buffer.set(msg.seq, msg); return requestRange(last + 1, msg.seq - 1); }
  await apply(msg); last = msg.seq;
  while (buffer.has(last + 1)) { const next = buffer.get(last + 1); buffer.delete(last + 1); await apply(next); last = next.seq; }
}
```

## Common traps
- **Sorting by the sender's timestamp.** Phone clocks drift; the server sequence is the truth.
- **Async handlers in parallel** reorder messages.
- **Ignoring gaps**: a missing message silently disappears.

## See it yourself
In a chat app, send several messages quickly from two devices on a flaky network and compare the order on each device: good apps converge to the same order.

## Quick quiz
<details><summary>Why not order chat messages by the sender's timestamp?</summary>

Device clocks can be wrong or skewed; a server-assigned sequence number is reliable.
</details>
<details><summary>What do you do when message 45 arrives but you last applied 42?</summary>

Buffer 45 and fetch 43–44, then apply them in order.
</details>
<details><summary>How can an async onmessage handler break ordering?</summary>

If message 1 awaits something slow (e.g. decryption) and message 2 doesn't, 2 finishes first. Process through a queue.
</details>
