## Key points
- **AbortController** really **cancels** a fetch: `controller.abort()` stops the request and rejects the promise with an `AbortError`.
- In React effects, **abort in the cleanup**, and ignore `AbortError` (a cancel isn't a failure).
- `AbortSignal.timeout(5000)` gives you a built-in timeout.

## Interview answer
> AbortController lets me cancel in-flight work. I pass its signal to fetch, and calling abort stops the network request and rejects the promise with an AbortError. In an effect I abort in the cleanup, which both prevents races and saves bandwidth when the component unmounts or the query changes, and I treat AbortError as expected rather than showing an error. AbortSignal.timeout creates a signal that aborts after a delay. Aborting a POST doesn't undo it if the server already received it, so mutations need idempotency keys.

## The analogy
Cancelling a cab booking. The driver turns around instead of just being ignored when they arrive. But if they've already dropped your parcel off, cancelling doesn't bring it back.

## How it works
```jsx
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal: controller.signal })
    .then(r => r.json())
    .then(setResults)
    .catch(err => { if (err.name !== 'AbortError') setError(err); });   // a cancel isn't an error
  return () => controller.abort();                                       // new query or unmount → cancel
}, [query]);
```

```js
// Timeout after 5 s
const res = await fetch('/api/report', { signal: AbortSignal.timeout(5000) });
```

## Common traps
- **Showing an error toast for AbortError.** It's expected when users type quickly.
- **Thinking abort undoes a POST.** The server may have processed it. Use an idempotency key and check the status.
- **Reusing one controller** after it's aborted. Create a new one per request.

## See it yourself
DevTools → **Network** → type quickly in a search box that uses AbortController: earlier requests show **(canceled)** in red.
